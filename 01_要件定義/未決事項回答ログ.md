## Q1. 日付の表記ゆれの格納方式（最優先）

- **決定**: 確定日カラム + 原文カラム + 精度フラグの3カラム構成
  - `EventDate`（nullable, date）… 推定代表日。並び替え・期間フィルタに使う
  - `EventDateText`（原文, 例「9月上旬」「秋頃」「予約受付中」）… 画面表示に使う
  - `EventDatePrecision`（enum: Exact / Month / Season / Ongoing / Unknown）
- **根拠**: BRIEF の「日付順タイムライン」を成立させるには並び替え可能な日付が要る。一方で曖昧表現を捨てると表示が痩せる。両立させるため代表日＋原文＋精度の3点持ちとした。後から精度フラグを足すのはマイグレーションが重いため最初から持つ。

## Q2. 対象範囲

- **決定**: アニメ・漫画を中心に据えるが、テーマ・カテゴリ構造は特定ジャンルに依存しない汎用設計にする
- **根拠**: ポートフォリオとしての物語（追いにくいアニメ・漫画情報を集約）を明確にしつつ、将来ジャンル拡張してもスキーマ変更が要らないようにする。テーマ＝任意キーワードで既に汎用。

## Q3. カテゴリ区分

- **決定**: 現行5区分に「ゲームセンター」を独立カテゴリとして追加し、「その他」を加えた **7区分**
  - グッズ / アニメ / 漫画 / イベント / ゲーム / **ゲームセンター（アーケード・プライズ・クレーンゲーム景品等）** / その他
- **根拠**: 開発者の指定。ゲームセンターのプライズ/アーケード情報を「グッズ」や「ゲーム」に混ぜず独立で追える方が実利用に合う。分類不能は「その他」に退避。DB は enum で保持し拡張しやすくする。

## Q4. 最初に実装する情報源3つ

- **決定（改訂）**: 開発者の方針転換により、グッズ・ゲームセンター（プライズ）情報を主軸に据える「B案」で確定。以下3つ。
  1. **MANTANWEB（まんたんウェブ）** — `https://mantan-web.jp/`（RSS: `https://mantan-web.jp/rss/mantan.xml`（着手時要確認））。アニメ/漫画/ゲーム/ラノベを広くカバー
  2. **HOBBY Watch（インプレス）** — `https://hobby.watch.impress.co.jp/`（RSS URL は着手時に特定）。フィギュア/グッズ/**プライズ（メーカー別：タイトー・セガ 等）**
  3. **Gamer** — `https://www.gamer.ne.jp/`（RSS は着手時要確認）。ゲーム/**アーケード・ゲームセンター**筐体・ロケテ・イベント

- **改訂の経緯**: 当初案（アニメ！アニメ！／マイナビニュース／ASCII.jp）は汎用ニュース寄りだった。開発者から「グッズ・ゲームセンター情報がメインになる情報源」を求められ、7カテゴリ（特にグッズ・ゲームセンター）に情報が乗る構成へ差し替えた。

- **検証状況（重要）**: **本セッションの環境ネットワークポリシーにより、外部ホストへの HTTP アクセスが全て 403（policy denial）で拒否され、RSS 本体・robots.txt・利用規約を実地検証できなかった。** 以下は WebSearch（二次情報）にもとづく確度評価であり、**RSS URL の生死・robots・規約の実地確認は着手時（Phase 1）に必須**とする（CLAUDE.md §0-4 の方針に合致）。

  | 検討サイト | RSS（二次情報の確度） | 根拠・カバー範囲 | 判定 |
  |---|---|---|---|
  | MANTANWEB | 中〜高（`/rss/mantan.xml` が具体的に報告） | 毎日新聞系の一次メディア。アニメ/漫画/ゲーム全般。権利面が比較的クリーン | 採用 |
  | HOBBY Watch | 中〜高（インプレスは全メディアで RSS 提供の慣行。正確なURLは未特定） | グッズ/フィギュア/プライズをメーカー別に整理。**ゲームセンター・グッズの主軸** | 採用 |
  | Gamer | 中（運営「イード」＝アニメ！アニメ！/インサイドと同社。同社インサイドは公式RSS一覧あり） | アーケード新作・ゲーセン筐体・ロケテ・イベント | 採用 |
  | タイトー/セガ/バンナム（プライズ公式） | ❌ RSS 見当たらず | 一次情報で権利はクリーンだが、RSS無し＋JS動的描画で AngleSharp では取りづらい | **将来Phase送り**（専用パーサー＋規約確認）。当面は HOBBY Watch/電撃ホビーウェブ経由で代替 |
  | コミックナタリー(natalie.mu) | 不明 | CDN が bot 遮断の疑い | **将来Phase送り**（規約確認・許諾前提） |
  | アニメイトタイムズ(animatetimes.com) | ❌ 公式RSS無し | HTMLスクレイピング必須 | **将来Phase送り**（専用パーサー＋規約確認） |

- **保留事項**: タイトー等ゲームセンター公式・ナタリー・アニメイトタイムズは「将来Phaseで再検討」。採用時は利用規約を人手で確認し、専用パーサーで対応する前提。第一陣3サイトも、着手時の実地確認で RSS が使えないと判明した場合に備え、代替候補（電撃ホビーウェブ、アニメージュプラス、アキバ総研 等）を控えとして記録しておく。

## Q5. Web 構成

- **決定**: ASP.NET Core + Blazor Server（BRIEF準拠）
- **根拠**: 利用者2名・localhost運用に対し単一プロセスで完結でき学習コストが低い。C# 未経験の現状で SPA 分離より優先度が低い。ポートフォリオでも .NET 理解を示せる。

## Q6. LLM 選定

- **決定**: Claude API（収集時の構造化のみ）
- **根拠**: BRIEF準拠。通知時は使わずコストをユーザー数に比例させない。モデルIDは実装着手時に最新を確認。抽象化（インターフェース）して差し替え可能にはしておく。

## Q7. 日本語全文検索

- **決定**: pg_trgm を導入し、タイトル・要約の部分一致に GIN インデックスを張る
- **根拠**: 小規模データで導入が軽く、VPS移行時も PostgreSQL 拡張として同様に導入できる。pg_bigm は精度は高いが Docker イメージへの導入がやや重く、現段階では過剰。将来必要なら差し替え可能。

## 確定済み（質問不要だった事項）

- DB は PostgreSQL（BRIEF §10.3 で確定）。Docker Compose でローカル起動。
- UTC保存/JST表示、冪等性のDB制約担保、収集と通知の分離、通知時にLLM不使用、権利配慮、LINE無料枠対応、VPS移行前提のOS非依存 — すべて BRIEF の確定制約として要件に引き継ぐ。
