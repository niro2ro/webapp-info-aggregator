## Q1. 日付の表記ゆれの格納方式（最優先）

- **決定**: 確定日カラム + 原文カラム + 精度フラグの3カラム構成
  - `EventDate`（nullable, date）… 推定代表日。並び替え・期間フィルタに使う
  - `EventDateText`（原文, 例「9月上旬」「秋頃」「予約受付中」）… 画面表示に使う
  - `EventDatePrecision`（enum: Exact / Month / Season / Ongoing / Unknown）
- **根拠**: BRIEF の「日付順タイムライン」を成立させるには並び替え可能な日付が要る。一方で曖昧表現を捨てると表示が痩せる。両立させるため代表日＋原文＋精度の3点持ちとした。後から精度フラグを足すのはマイグレーションが重いため最初から持つ。

## Q2. 対象範囲

- **決定**: アニメ・漫画を中心に据えるが、テーマ・カテゴリ構造は特定ジャンルに依存しない汎用設計にする
- **根拠**: ポートフォリオとしての物語（追いにくいアニメ・漫画情報を集約）を明確にしつつ、将来ジャンル拡張してもスキーマ変更が要らないようにする。テーマ＝任意キーワードで既に汎用。

# 追補: レビュー第2回で確定した設計判断（2026-08-05）

要件定義書 v1.0 ドラフトのレビューで浮上した論点を開発者と確認し、以下を確定した。

## Q8. お気に入りテーブルの構造

- **決定**: 単一 `Favorites`（`target_type`+`target_id` のポリモーフィックFK）を廃し、`FavoriteThemes(user_id, theme_id)` と `FavoriteSources(user_id, source_id)` に**テーブル分割**する。
- **根拠**: ポリモーフィックFKは行ごとに参照先が変わるため DB で FK 制約を張れず、削除済みテーマ/ソースを指す孤児レコードを防げない。CLAUDE.md §5「DB制約を最終防衛線に」に反する。分割すれば各テーブルに本物の FK と `ON DELETE CASCADE` を張れ、整合性を DB が保証する。利用者2名・小規模でテーブル統合の利得は薄く、整合性の利得が勝る。列挙型 `FavoriteTargetType` は不要となり廃止。

## Q9. タイムラインの NULL 日付整列

- **決定**: `event_date` が NULL（precision=Unknown/Ongoing）の記事は `created_at` を代理キーに整列し、新着として扱う。整列キー = `COALESCE(event_date, created_at::date)`。式インデックスを張る。
- **根拠**: 「日付が確定していない新着（予約受付中・受注開始等）」はユーザーにとって"新しい情報"であり、末尾に沈めるより新着上位に見せる方が体験に合う。DB 依存の NULL 整列でブレないよう式で明示。NFR-04（一覧2秒）担保のため式インデックスを付与。

## Q10. データ保持パージとブックマークの衝突

- **決定**: 記事パージ（NFR-05）の対象から、**いずれかの利用者が Bookmarks に保存済みの記事を除外**する。パージは「Bookmarks に無い・かつ created_at が保持期間超」の記事のみ。付随データ（ReadStates/ArticleThemeMatches/ArticleNotifications）は ON DELETE CASCADE で連動削除。（保持期間は当初6ヶ月だったが Q13 で対象期間に合わせて改訂。最終的に**2年**＝前年同期比較のため。）
- **根拠**: ユーザーが「後で見る」で明示保存した記事を自動削除するのは意図に反する。保存の有無をパージ条件に組み込むことで保存性を担保する。

## Q11. enum のコード値保持方式（確認）

- **決定**: PostgreSQL native enum ではなく `smallint` コード値＋コメントで保持。承認。（Java では JPA の `AttributeConverter`＋`@Convert` で enum ↔ コード値を変換。Q12 参照）
- **根拠**: native enum は値のリネーム/削除/並べ替えの ALTER が面倒でマイグレーションと噛み合わせづらい。smallint は pg_dump/restore・VPS移行で無難。カテゴリ追加はアプリ側 enum に値を足すだけでスキーマ変更不要。センチネル値（9=その他）で拡張余地も確保。※Hibernate 既定の `@Enumerated(ORDINAL)` は列挙順に暗黙依存し危険なため使わず、コード値を明示する Converter を挟む。

# 追補: 技術スタックのピボット（2026-08-05）

## Q12. 実装言語・技術スタックを C#/.NET から Java へ変更

- **決定**: 本プロジェクトを **Java（Spring Boot + Vaadin Flow）学習を兼ねたポートフォリオ**へピボットする。当初の C# / .NET（Blazor Server）想定を全面的に置き換える。
- **経緯**: 開発者の判断により、ポートフォリオで示す技術を Java に変更。これに伴い CLAUDE.md（§0-3/§2/§3/§4/§5/§6/§7）と要件定義成果物の技術記述を改訂した。
- **重要な原則**: **要件そのもの（機能一覧 FR・非機能 NFR・画面 SC・データ設計 TBL/DDL・外部I/F・エラー方針・冪等性/UTC 等の制約）は言語に依存しないため不変。** 変更したのは技術構成（D5 と実装メモ）のみ。ウォーターフォールで要件を先に固めた利点がそのまま活きる形。

- **Web 構成（D5）の選定**: 開発者に3案（Vaadin Flow / Spring Boot+Thymeleaf+htmx / REST API+SPA）を提示し、**Vaadin Flow** を選択。
  - **根拠**: Blazor Server と同じ「サーバー側で UI 状態を持つステートフルな単一プロセス UI」を Java で最も近く再現でき、当初 D5 の選定理由（学習コスト低・localhost・別フロント不要）をそのまま引き継げる。別フロント（JS/SPA）の学習を避けられ、Java + Spring の学習に集中できる。

- **技術スタック対応（.NET → Java）**:
  | 層 | 旧（.NET） | 新（Java） |
  |---|---|---|
  | 言語/実行 | C# / .NET 8 | Java 21 (LTS)・仮想スレッド |
  | 基盤/DI | .NET 組込 DI | Spring Boot 3.x |
  | ビルド | （MSBuild/sln） | Maven マルチモジュール |
  | Web | ASP.NET Core + Blazor Server | Spring Boot + **Vaadin Flow** |
  | バッチ | コンソール(Generic Host) | Spring Boot 別アプリ + CommandLineRunner |
  | ORM | Entity Framework Core | Spring Data JPA + Hibernate |
  | マイグレーション | EF Core Migrations | **Flyway（SQLベース）** |
  | HTTP/回復性 | HttpClientFactory + Polly | RestClient + Resilience4j |
  | HTML解析 | AngleSharp | jsoup |
  | RSS | System.ServiceModel.Syndication | ROME (rome-tools) |
  | LLM | Claude API（自作抽象化） | Claude API（anthropic-sdk-java 公式） |
  | 通知 | LINE Messaging API（自作） | line-bot-sdk-java（公式） |
  | 設定/秘密 | appsettings + User Secrets | application.yml + 環境変数/.env |
  | テスト | xUnit | JUnit 5 + Mockito + Testcontainers |

- **考え方の差分（開発者への説明ポイント）**:
  - **async/await 未経験問題の解消**: Java 21 の仮想スレッドを使えば、通常の逐次（ブロッキング）コードのまま高い並行性が得られ、C# の async/await に相当する学習負荷を避けられる。LINQ に相当するのは Stream API。
  - **マイグレーション**: EF Core のコードファースト自動生成に代えて **Flyway で DDL(SQL) を手書き**する。DB 設計が得意な開発者（Delphi/ERP 出身）にはむしろ自然で、テーブル定義書がそのまま `V1__*.sql` になる。
  - **enum**: Hibernate 既定の `@Enumerated(ORDINAL)` は列挙順に暗黙依存し危険なため使わず、コード値を明示する `AttributeConverter`（`@Convert`）を挟む（smallint コード値方式 Q11 と整合）。
  - **時刻**: Java の `ZoneId` は IANA tz 名（"Asia/Tokyo"）で全OS共通のため、.NET のような Windows/Linux 識別子差異は無い。UTC 保存/JST 表示の原則（NFR-08）は不変。

- **一次入力 PROJECT_BRIEF.md の扱い**: 当初は原文（.NET 想定）を保持する方針だったが、**開発者の追加指示により Java 前提へ更新済み**（冒頭にピボット追記あり）。確定判断と根拠は本回答ログ（特に Q12）を正とする。
- **後工程 skill の扱い**: `03_詳細設計` / `04_Code` / `05_単体テスト` の各 skill（`.claude/skills/`）、および `01_要件定義` skill の Web 構成の問いを **Java 前提へ改訂済み**（同追加指示による）。`02_基本設計` / `06_結合テスト` skill はフレームワーク非依存で .NET 記述が無いため変更不要だった。

# 追補: 対象範囲（スコープ）の確定（2026-08-05）

## Q13. 対象範囲（スコープ）を明文化

Q2（対象範囲＝アニメ・漫画中心／汎用構造）を、要件定義書 §1「対象範囲（スコープ）」として具体化し確定した。

- **対象ドメイン**: アニメ・漫画の最新情報（カテゴリ8区分で表現。「コラボ」は横断情報でイベント/グッズに分類）。※種別は既存のカテゴリ構造で表現済み（カプセルトイの追加は Q14）。
- **スコープ内**: 収集・一覧表示・LINE 通知。
- **スコープ外（今回やらない）**: 記事本文/画像の保存・表示、利用者間の共有・コメント、価格比較、在庫連携、購入・予約・SNS 投稿。
- **将来の機能追加候補**: 在庫情報、利用者数拡大（3名以上）、汎用アグリゲーター化。
- **境界条件**: 日本語・国内サイトのみ／利用者2名固定／対象期間＝直近**2年分**。
- **拡張方針**: アニメ・漫画に特化して提示。構造は汎用のままとし将来拡張の余地を残す。

- **根拠**: ポートフォリオとして「範囲を切る判断（＝あえてやらないことの明示）」を見せるため、スコープ外と将来候補を分けて記録した。範囲を明示することで Claude Code による実装が意図から逸れないようにする狙いもある。
- **対象期間を2年分とする根拠（ドメイン判断）**: アニメ・漫画では前年と同時期・同種の新作（周年記念グッズ、季節イベント、シリーズ続編・再放送等）が出る傾向がある。前年同期の情報と比較できるよう、直近1年ではなく**2年分**を対象・保持する。

- **NFR-05 との整合**: 「対象期間＝2年分」に合わせ、データ保持期間を当初の**記事6ヶ月 → 2年**へ改訂（Q10 のブックマーク除外ルールはそのまま、閾値のみ2年に変更）。ログは1ヶ月のまま。データ量は利用者2名・小規模のため2年でも問題なし（NFR-04 の一覧2秒に影響しない見込み）。

## Q14. 目的・成功基準の明文化、およびカプセルトイの独立カテゴリ化

要件定義の項目1「スコープ・目的」を詰める中で、システム化の目的と成功基準を開発者に確認し、要件定義書 §1 に記録した。

- **目的**: アニメ・漫画のグッズ、ゲームセンターのプライズ、カプセルトイ（ガチャ）などの最新情報は媒体に分散し追うのが大変で、人気商品はすぐ売り切れる。1か所に自動集約し新着を効率よく把握できるようにする。Java 学習を兼ねた転職用ポートフォリオ。
  - **正直な線引き**: 収集は「PC 起動時にまとめて取得」方式で即時アラートではない。目的は「集約して探す手間を減らす」こと。即時性は Phase 6（時刻ベース通知）で高める。
- **成功基準**: ①テーマ登録→自動収集（RSS 主・必要箇所のみ LLM 構造化）→一覧・検索、②お気に入り新着を LINE に1通通知、③利用者2名のデータが混ざらず一通り不具合なく動作（協力者テストで確認）、④AI 利用は収集時の構造化のみで月500円以内。
- **成功基準の表現を設計と整合させた点**（重要）: 開発者の当初案は「LLM がグッズ・アニメの最新情報を取得し…」だったが、本設計では **LLM は情報取得ではなく RSS で取れない箇所の構造化のみ**（D6・NFR-06・§7.0）。「AI コストをユーザー数に比例させない」設計判断と矛盾しないよう、「RSS を主とし必要な箇所のみ LLM で構造化」と表現を修正した。また「テーマを検索し」→「テーマを**登録**すると収集される」（検索 FR-04-03 は収集済みからの絞り込みで別機能）に正した。

- **カプセルトイの独立カテゴリ化**: 目的にカプセルトイ（ガチャガチャ）が明記されたため、分類先を確認。「グッズに含める／ゲームセンターに含める／独立追加」の3案から **独立カテゴリを追加**を選択。
  - **決定**: Category enum に `7:カプセルトイ(ガチャ)` を追加し、カテゴリを **7区分 → 8区分**（グッズ/アニメ/漫画/イベント/ゲーム/ゲームセンター/カプセルトイ/その他）に拡張。
  - **根拠**: 開発者の主要関心の一つであり、グッズ（一般物販）やゲームセンター（アーケード/プライズ）と混ぜず独立で追えた方が実利用に合う。smallint コード値方式（Q11）のため enum に値を足すだけでスキーマ変更は不要（センチネル 9:その他 の手前 7 に採番、8 は将来余地）。

|---|---|---|---|
| G1 収集バッチの定期自動実行 | ①自動収集 | **運用要件のまま（非FR）** | §3 FR-06 直後の注記。Phase 5＝タスクスケジューラ／Phase 6＝cron。アプリはヘッドレス実行可（NFR-09）で担保、手動起動は FR-06-02 |
| G2 LINE連携設定（ID登録・通知全体ON/OFF） | ②LINE通知 | **FR・画面を追加** | FR-07-03、SC-09。`Users.line_user_id` / `Users.notify_enabled` を画面で管理 |
| G3 LLM利用状況の可視化（回数・コスト） | ④月500円以内 | **記録・確認FRを追加** | FR-06-06、SC-07、TBL-LlmUsageLogs、enum LlmCallStatus。LINE 通数管理（FR-06-04）の LLM 版 |
| G4 利用者2名の登録・管理 | ③2名分離 | **管理機能を持つ** | FR-07-02、SC-09。初期2名は seed、以降は画面から追加可 |

- **根拠**:
  - G1＝FR は「アプリが何をするか」。定期起動は OS のスケジューラ／cron の仕事でアプリ機能ではないため運用要件に置く。ポートフォリオ観点でも「機能要件と運用要件の切り分け」を示せる。アプリ側は別プロセス・ヘッドレス実行できる設計（NFR-09）で運用要件を成立させる責務だけ負う。
  - G2＝②を動かすには送信先 `line_user_id` と通知の大元スイッチが要る。「手動登録でよい」の当初方針だけでは利用者が自分で連携・停止できず片手落ちのため、上位マスタスイッチとして FR 化（お気に入り単位 ON/OFF＝FR-05-04 の親）。
  - G3＝④「月500円以内」は数値目標（NFR-06）だが、測る手段が無ければ検証できない。LINE 通数を DB 記録して残量表示する設計（FR-06-04）と対称に、LLM も回数・トークン・概算コストを記録し可視化する。**上限接近時も収集は止めず可視化のみ**（LINE は通数が有限資源のため送信停止するが、LLM コストは自己負担の目安であり機能停止は過剰）。
  - G4＝③の「2名」をどう作るかが未定義だった。認証（FR-07-01）はあるがユーザー生成手段が無い。2名固定でも seed だけだと片方が増員・改名できないため、最小の管理機能（追加・編集）を持たせる。スコープ「利用者2名固定」とは矛盾しない（固定は既定値であり、画面での増減余地を残すのは将来拡張候補 Q13 とも整合）。
- **照合結果**: 上記4点の反映により、成功基準①〜④それぞれに対して「実現する機能」と「検証する機能」が FR/画面/データ設計で追える状態になった。

## Q16. 認証・認可の実装レベル（非機能 項目3 の詰め・2026-08-07）

非機能要件の★項目「セキュリティ・認証/認可」を実装レベルまで確定した。要件定義書 NFR-02・FR-07・TBL-Users・画面一覧・§8 に反映。

- **認証（Authentication）**:
  - 一般利用者(user): ログイン画面に有効な利用者の [ID＋表示名] 一覧を表示し、**クリックで選択ログイン**。パスワード入力なし。
  - 管理者(admin): 選択後に **4桁PIN** を入力し `Users.admin_pin_hash`（BCrypt）と照合。連続失敗で一時ロック。
- **認可（Authorization）**: `Users.role`（enum `UserRole` 1:User / 9:Admin）で2ロール。管理系画面（SC-06 情報源マスタ／SC-07 管理ダッシュボード＝**LLMコスト含む**／SC-08 実行ログ／SC-09 利用者管理）は **admin 限定**。Spring Security（`@PreAuthorize` 等）で制御。
- **段階化**: ローカル(Phase 5)は上記。**VPS(Phase 6)で全利用者を本格認証（パスワード/OAuth）へ差し替え**、認可(role)層は不変。
- **データ変更**: `TBL-Users` の `login_key`（旧・簡易認証キー）を廃止し、`role` と `admin_pin_hash` を新設。enum `UserRole` を追加。

- **決定の経緯と根拠**:
  1. 当初提案は「Spring Security＋フォーム認証（ID/パスワード）＋admin/user」だったが、開発者判断で**ログインUIを利用者選択方式（一覧クリック）に変更**。日常利用の手間を最小化する狙い。
  2. これは厳密には「認証（本人証明）」ではなく「**識別**（誰として使うかの選択）」であり、鍵が無い。自宅PC・信頼できる2名という脅威モデルでは合理的（Windows/Netflix のユーザー選択と同発想）と判断。
  3. ただし鍵なしだと**管理者ロールが誰でも選べてしまい、admin限定（例: LLMコスト画面）が“画面整理”の意味しか持たない**。この弱点を解消するため、開発者判断で **管理者選択時のみ4桁PIN** を課すことにした。これで管理系は最小の鍵で保護される。
  4. **authN（ログイン方式）と authZ（ロール制御）を分離**し、認可は Spring Security で本物として効かせる。ローカルは認証を「選択＋PIN」にし、VPSでは**認証方式だけをパスワード/OAuthへ差し替え**て認可層は不変にする。この分離自体が、認証と認可を理解している証明としてポートフォリオの説明ポイントになる（"簡易認証"の曖昧語を廃止できる副次効果も）。
  5. 4桁PINは低エントロピー（10000通り）で総当たり可能なため、**連続失敗ロック**を補助的に入れ、位置づけを「ローカル向け最小認証・VPSで本格化」と明記した。

## Q17. 秘密情報・設定の外部化方式（非機能 項目3 の詰め・2026-08-07）

非機能★「拡張性・移行性」のうち秘密情報の管理方式を確定した。要件定義書 NFR-11 に反映。

- **決定（案A：環境変数で外部化）**:
  - **機密**（LINEトークン／Claude APIキー／DBパスワード等）は**環境変数のみで注入**。`application.yml` はプレースホルダ `${...}` のみとし、実値をリポジトリに置かない。ローカル＝`.env`（gitignore）、VPS＝systemd `EnvironmentFile` 等。
  - **非機密の環境差分**（DBホスト・ログレベル・User-Agent連絡先等）は **Spring Profiles**（`application-{profile}.yml`）で切替。
  - 12-factor 準拠として NFR-11 に明記。
- **検討した代替案**（開発者に5案を提示して比較）:
  - B. リポジトリ外の設定ファイル（`spring.config.additional-location`）… 手軽だがファイル配布が手作業で説明価値低め。
  - C. 暗号化してリポジトリにコミット（**Jasypt** / SOPS / git-crypt）… 秘密を暗号化した状態でGit管理でき、管理鍵はマスターキー1個。**ポートフォリオで一段深く見せられる**が学習コスト増。
  - D. 専用シークレットストア（Vault等）… 企業標準だがサーバー運用が要り、2名・単一VPSには過剰。
  - E. OS資格情報ストア（Windows資格情報マネージャ等）… **OS依存でNFR-09に反する**ため不採用。
- **根拠**: 自宅PC→単一VPS・2名という規模では、案Aが**手間最小で移行性・安全性を両立**し説明も容易。秘密情報の誤コミットという最大級の減点を、環境変数化＋プレースホルダのみで確実に回避できる。
- **将来余地（設計メモに記載）**: 案C（Jasyptで暗号化コミット）は「秘密の履歴管理・より高度な見せ方」として選択肢に残す。必要になれば後日検討してよい（ただし復号マスターキーの環境変数管理は結局A方式と同様に必要で、本質的な追加安全性は限定的）。

## Q18. アプリのコンテナ化レベル（非機能 項目3 の詰め・2026-08-07）

非機能★「拡張性・移行性」のうちコンテナ化方針を確定した。要件定義書 NFR-12・§11(Phase 6) に反映。

- **決定（Docker 採用・折衷案）**:
  - **開発中**：アプリ本体（web/batch）は JAR / IDE で直接実行、**PostgreSQL のみ Docker Compose**（Phase 0 で導入済）。
  - **Phase 6 VPS 移行時**：アプリもコンテナ化（マルチステージ `Dockerfile`）し、`docker compose` で web／batch／db を一括起動。
  - 秘密情報は compose の `env_file`／環境変数で注入（NFR-11 案A と整合）。
- **検討した代替案**:
  - (a) 最初から全面 Docker … 環境差異ゼロだが、Vaadin の自動リロードにマウント設定が要り、Java 学習中の開発反復が重くなる。
  - (b) Docker 化しない（`java -jar`＋systemd）… 最小・移行は可能だが、ポートフォリオに Docker スキルを載せられない。
- **根拠**:
  1. **Docker は移行の必須条件ではない**（JAR は元々OS非依存）。採用理由は「①Windows→Linux の環境差異解消による移行の安全化 ②ポートフォリオでの Docker スキル証明」の2点。
  2. 開発中のコンテナ化は Vaadin の反復速度を落とすため見送り、**成果物として残る Phase 6 で導入**するのが費用対効果に優れる。
  3. バッチは常駐せずワンショット実行（`CommandLineRunner`）でWebと起動モデルが異なるため、コンテナ化と定期実行（運用要件・G1）は Phase 6 で併せて設計する。
- **補足**: Docker の概念解説（コンテナとは／VMとの違い／image・container・Dockerfile・registry の用語／既に PostgreSQL で使用中）は設計メモ（`設計メモ.html`）に補足ボックスとして記載した。

## Q21. LLMコスト管理（ハードキャップ・案A・Sonnet）（項目5外部制約の詰め・2026-08-07）

非機能★「外部制約への対応」のうち LLM コスト管理を確定。要件定義書 NFR-06・FR-02-11・FR-06-06・D6・§7.2 に反映。

- **①コスト上限＝ハードキャップ**: 月次上限（500円）に達したら **LLM 構造化を停止し RSS/専用パーサーで収集継続**（収集・一覧表示は止めない）。安全マージン（例:90%）で手前停止。判定は `LlmBudgetGuard`（LLM呼び出し前に当月累計を確認）に集約し、取得3段フォールバック（FR-02-04）の LLM 段だけをコストで閉じる。
- **コスト算出＝案A（usage自前計算）**: 各APIレスポンスの `usage`（入出力トークン数）× モデル単価（`application.yml`）で概算し `LlmUsageLogs` に記録。当月累計は `SUM(est_cost_micro_jpy)`（JST月）で算出。組織のAdmin使用量/コストAPIは**実請求との突合（任意）**に位置づけ、ハードキャップの判定には使わない（Adminキー要・集計遅延あり・組織単位のため）。
- **使用モデル＝Claude Sonnet**: 標準単価 入力$3/出力$15（100万トークンあたり）。1記事の想定トークン（入力≒2,000/出力≒300）で **≒¥1.6/記事**、月500円で**約300記事/月（≒1日10記事）**。開発者判断で「1日10記事も使わない」見込みのため Sonnet を採用（Haiku なら約3倍こなせるが、品質と余裕を優先）。単価は改定されうるため実装着手時に公式ドキュメントで確認し `application.yml` に設定。
- **根拠**: 「月500円以内」を目標から**守れる設計（ハードキャップ）**に格上げしつつ、前回G3の「収集は止めない」方針と両立（LLM段のみ停止、RSSで継続）。案Aは呼び出し前に当月累計を即時に判定できる唯一現実的な方式（Admin API は用途に不適）。Sonnet 採用は実利用ボリュームが小さいという開発者の見立てに基づく。

## Q22. LINE通知失敗の分類・再送方針（項目5外部制約/項目8エラー方針の詰め・2026-08-07）

(2)LINE配信失敗時の再送ポリシーを起点に、通知失敗の全分類と受信側の扱いを確定。要件定義書 §8.1・FR-03-07/08・FR-04-06・FR-07-03・NotifyStatus enum・ArticleNotifications に反映。

- **分類（NotifyStatus）と再送方針**（判別＝HTTPステータス＋例外種別）:
  - ①TempError（5xx/接続断）・②RateLimited（429）＝同一実行内で秒単位リトライ→ダメなら未通知を残し**次回PC起動時に再送**。
  - ③AuthFailed（401）・③Blocked（ブロック/未追加）＝自動リトライせず未通知を残す（原因解消後の次回に届く）が**5日超過で打ち切り（GaveUp）**。
  - ④FormatError（400）＝**打ち切り**（同形式で必ず失敗＝不具合、スキップしログのみ）。
  - ⑤Timeout（応答不明）＝**冪等キー（X-Line-Retry-Key 相当）付きで再送**し二重配信を防ぐ。
  - まとめ：再送する＝①②③⑤／打ち切り＝④・③の5日超過。
- **常駐しないバッチ前提の重要点**: 「再送」は原則**次回PC起動時**。②の「バックオフ」も“1時間後”ではなく次回起動（プロセス内で長時間眠らない）。VPS常駐化（Phase 6）で初めて「N分後に再送」が現実的になる。
- **判別可否の正直な整理**: ①(5xx)②③認証④は HTTP で判別可。判別が難しいのは **⑤タイムアウト（届いたか不明）** と **③ブロック（pushでは失敗と分からずwebhook要）** の2つ。⑤を①と分けて冪等キー扱いにする理由がこれ。
- **送信側の可視化**: 失敗を分類し `NotificationLogs.status`(=NotifyStatus) に記録、SC-07/SC-08 に**分類別の管理者向けメッセージ**（次アクションが分かる文面）を表示。開発者判断「分類ごとに“この原因でエラー”と出す」案を採用（管理者向け。一般利用者には詳細を出さない）。
- **受信側の扱い（開発者の問い「届く側はどうする」への結論）**: **アプリが情報の正／LINEは補助的プッシュ**。新着は送信の成否に関係なく必ずアプリ内（タイムライン）に入るため、LINE失敗でも受信側は取りこぼさない（FR-04-06 未通知の可視化）。受信側がアクションを要するのは③ブロック/未追加のみで、SC-09 の LINE連携ステータス＋友だち追加案内で自己解決。
- **カルーセル上限**: バブル上限（LINE仕様上おおむね12件・着手時確認）超過は**切り詰め**（無料枠を余計に消費する分割送信はしない）。推奨案として採用。
- **データ表現**: `ArticleNotifications` に `result`(0:Delivered/1:GaveUp) を追加。未通知＝行が無い状態。失敗(①②③⑤)は行を作らず未通知のまま、成功と打ち切りのみ行を作り再送対象から外す。
- **打ち切り日数**: ③の未通知は**5日超過で打ち切り**（開発者判断）。
- **根拠**: 「再送する失敗／しない失敗の切り分け」を設計で示す（③④は再送しても無駄→停止＋メッセージ、⑤は冪等キーで安全に再送）。LINE仕様（冪等キー・カルーセル上限・ブロック検知）は改定されうるため着手時に公式確認（CLAUDE.md §4）。

- **2段の遵守ゲート**:
  - **規約ゲート（人手・情報源単位）**: `Sources.terms_reviewed=true`（＋確認日・規約メモ）の情報源だけ収集対象。未確認は登録できても収集しない（未確認は集めない）。第一陣3サイトも規約OKを確認して立てるまで収集されない。
  - **robots ゲート（自動・ページ単位）**: 各URL取得の直前に robots.txt を判定し Disallow のパスはスキップ→`CrawlLogs` 記録。日次キャッシュ。パースは crawler-commons 等の定番ライブラリ。**取得エラー時は安全側で当日スキップ**（開発者判断）。robots が無い/取れない通常時は慣例どおり許可扱い。
- **役割分担の根拠**: 規約は機械判定不可→人手フラグ、robots は機械判定可→自動。効くタイミングも規約=収集開始前・情報源単位／robots=取得直前・ページ単位、と分離。
- **データ変更**: `Sources` に `terms_reviewed`(bool)/`terms_reviewed_at`/`terms_note`/`robots_respect`(bool既定true) を追加。FR-02-12（規約遵守ゲート）新設、FR-02-05（robots自動ゲート・エラー時当日スキップ・crawler-commons）を具体化。FR-06-01 に規約確認フラグ登録を追加。
- **開発者への説明**: robots.txt の概念（ボット向けの立ち入り可否の取り決め・技術的な鍵ではないがマナー/権利上尊重する）を要件定義書 §7.0 と設計メモに補足として追加（Java学習者向け）。用語定義に robots.txt / 遵守ゲート を追加。
- **根拠**: 「権利配慮を運用任せにせず仕組みで守る」はポートフォリオの評価点。RSS優先(§7.0)・本文非保存(§9)と並ぶ権利配慮の柱。robots/規約の具体値は改定されうるため着手時に実地確認（CLAUDE.md §4）。

## Q24. 発生日の種別（発売日順ソート・種別表示）（2026-08-07）

「発生日で見られるが発売日順でも見たい／ソートと表示に発売日を入れたい」という要望を、**案A（発生日に種別を足す）**で確定。要件定義書 Articles・enum・FR-02-06・FR-04-01/02・SC-02/03・§7.2・用語定義・ビジネスルールに反映。

- **背景の整理**: これまで日付は「発生日(代表日)」1本で、グッズ発売日/イベント開催日/放送日をまとめて持っていた。発売日順や種別表示を出すには「その日付が何の日か」を持つ必要がある。
- **案A採用（種別カラム、独立の発売日カラムは不採用）**: `Articles.event_date_kind`（enum `EventDateKind`＝1:発売日/2:開催日/3:放送日/4:受付開始/9:その他）を追加。1記事＝1つの主要日付という実態に合い、独立カラム（案B）で起きる発生日と発売日の値の重複・イベント/放送でのNULLを避けられる。
- **種別の決め方（3段・LLM最小化）**: ①カテゴリ既定マッピング（グッズ/カプセルトイ/ゲーム/漫画→発売日、アニメ→放送日、イベント→開催日、ゲームセンター/その他→その他）→②原文キーワード補正（発売→発売日/開催→開催日/放送・配信→放送日/予約・受付→受付開始）→③LLMを呼ぶ記事のみ出力に種別を含める。**種別のために LLM を新規に呼ばない**（§5 コスト原則・D6 と整合）。precision（確度）とは別軸。
- **UI/機能**: FR-04-01 の並び順に「発生日順（既定・全種別）／発売日順（種別=発売日を日付順）／収集日順」＋昇順降順。日付は種別ラベル付き表示（例「発売日 9/20」）。FR-04-02 フィルタに種別を追加。
- **根拠**: 目的「人気グッズを売り切れ前に把握」に対し、発売日順で近い順に並べられると直結する。ゲームセンター/漫画の既定マッピングは調整余地ありとして記録。

## Q27. 新規アカウント登録を非管理者に開放（2026-08-08）

開発者判断で「アカウント登録は管理者でなくても登録できるように」。ただし自己昇格の穴を作らない範囲で開放する方針を確認（AskUserQuestion→「新規登録は誰でも可・一般利用者として」を選択）。

## Q28. 利用者管理（SC-09）をログイン画面からアプリ内ドロワーへ移設（2026-08-08）

開発者判断で「アカウント登録は新規登録（誰でも）だけログイン画面に必要。管理者用の管理入口はログイン画面に不要。管理者でログイン後、メイン画面側に編集・削除・Admin付与を持つ」。Q26 で SC-09 をログイン前段に置いた判断を見直す。

## Q30. 配色テーマの方向性「和ノスタルジック（水彩・自然/黄昏）」（2026-08-08）

「夏目友人帳風のデザインにできる？」への対応。

- **方針（重要・権利配慮）**: 特定作品（夏目友人帳）の**ロゴ・キャラクター（例: ニャンコ先生）・公式ビジュアル・公式カラーをブランドとして流用しない**（§9「ロゴ/ビジュアルを使わない」・本プロジェクトの根幹方針と一致）。その代わり、作品が想起させる**空気感（和風・水彩・自然/黄昏の穏やかさ）をムードとして再現したオリジナル配色テーマ**を作る。IP の模倣ではない。
- **決定**: テーマ名「和ノスタルジック（水彩・自然/黄昏）」。ライトは和紙クリーム背景＋苔緑プライマリ＋墨茶文字、上部バーは黄昏の緑→藍グラデ、見出しは明朝体で余韻。カテゴリ色は彩度を落とした earthy 系に統一。ダークは焦茶ベースの暖色暗色。Lumo カスタムテーマの CSS 変数上書きで実現（プラグイン不要・BD-SC-00-09 と同じ方式）。
- **反映**: 画面設計書 §0.1 のトークン表を本テーマに更新。モックアップ（`画面モックアップ.html`）の配色・書体・バナーを差し替え。**要件（FR/NFR/データ）への影響なし**。配色はあくまで方向性で、開発者の好みで再調整可（indigo 版＝Q29 も履歴として残る）。
- **和柄の追加（2026-08-08 追補）**: 「色だけでなく和風柄も」との要望で、**七宝つなぎ（重ね円）**を地紋として背景・上部バー・ログイン画面に淡く敷いた。**七宝・青海波・麻の葉などは日本の伝統文様（非著作物）**であり、特定作品の柄ではないオリジナル実装。可読性優先で低透過に抑える。実装では CSS の重ねグラデ（モック採用）か軽量 SVG を Lumo テーマの背景に設定。§0.1 に「地紋（和柄）」行を追加。
