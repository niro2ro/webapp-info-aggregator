1. システム概要

アニメ・漫画などのテーマ（キーワード）を登録すると、関連する最新情報（グッズ・イベント・放送・コラボ等）を複数の情報源から自動収集し、発生日順の一覧で確認できる Web アプリケーション。お気に入り登録した対象に新着があれば LINE で通知する。

目的

アニメ・漫画のグッズ、ゲームセンターのプライズ、カプセルトイ（ガチャ）などの最新情報は複数の媒体に分散し追うのが大変で、人気商品はすぐ売り切れる。これらを1か所に自動集約し、見たいテーマの新着を効率よく把握できるようにする。あわせて、本プロジェクトは Java（Spring Boot + Vaadin Flow）習得を兼ねた転職用ポートフォリオとする。

補足: 収集は「PC 起動時にまとめて取得」方式であり、秒単位の即時アラートではない。目的は「1か所に集約して探す手間を減らす」こと。即時性は Phase 6（VPS・時刻ベース通知）で高める。

成功基準

  1. 見たいテーマ（キーワード）を登録すると、システムが複数情報源から新着を自動収集し（RSS を主とし、必要な箇所のみ LLM で構造化）、発生日順の一覧・検索で確認できる。
  2. お気に入り対象に新着が出たら LINE に1通で通知が届く。
  3. 利用者2名それぞれのテーマ・お気に入り・既読・通知が互いに混ざらず、画面・機能が一通り不具合なく動作する（協力者テストで確認）。
  4. （コスト）AI 利用は収集時の構造化のみで、月500円以内に収まる。
  • 想定利用者: 2名（開発者本人＋協力者1名）
  • 実行環境: 自宅 Windows PC（常時稼働しない）。バッチはタスクスケジューラでログオン時に起動。
  • 将来: 転職活動開始時に VPS へ移設（Phase 6・実施確定）。
  • 本プロジェクトは転職活動用ポートフォリオを兼ねる。

運用モデルに由来する前提

  • 通知は時刻ベースではなく「PC 起動時に前回以降の新着をまとめて届ける」方式。
  • 1日に複数回起動されうるため 冪等性の担保が必須（重複登録・重複通知をしない、同日2回目以降は通知しない）。

対象範囲（スコープ）

本システムが「どこからどこまでを扱うか」の線引き。ここで範囲外を明示することで、後工程の設計・実装が意図から逸れないようにする（決定根拠は回答ログ Q13）。

対象ドメイン: アニメ・漫画に関する最新情報。種別はカテゴリ8区分（グッズ／アニメ〔放送〕／漫画／イベント／ゲーム／ゲームセンター／カプセルトイ／その他）で表現する。「コラボ」は横断的な情報で、実体に応じてイベント（コラボカフェ等）やグッズ（コラボ商品）に分類する。

スコープ内（本プロジェクトで実現する）: - 情報の収集（複数情報源から自動収集） - 一覧表示（発生日順タイムライン・フィルタ・検索・未読既読） - LINE 通知（お気に入り対象の新着）

スコープ外（今回は実現しない）: - 記事本文／公式画像の保存・表示（自作要約＋元URLのみ） - 利用者間の共有・コメント等のソーシャル機能 - 価格比較・在庫連携 - 購入・予約・SNS 投稿等のアクション連携

将来の機能追加候補（今回は外すが拡張余地として記録）: - 在庫情報の取り込み - 利用者数の拡大（3名以上） - 汎用アグリゲーターとしての展開

境界条件: - 言語＝日本語のみ／対象サイト＝国内のみ - 利用者＝2名固定 - 対象期間＝直近2年分（DB 保持期間もこれに合わせる。NFR-05）。※前年と同時期・同種の新作（周年グッズ、季節イベント、シリーズ続編等）が出る傾向があり、前年同期と比較できるよう2年分を保持する

拡張方針: アニメ・漫画に特化した製品として提示する。テーマ／カテゴリ構造自体は特定ジャンルに依存しない汎用設計とし、将来の機能追加で汎用アグリゲーターとして見せられる余地を残す。

FR-03-08 二重送信防止（冪等キー） LINE push の冪等キー（X-Line-Retry-Key 相当・着手時に公式確認）を用い、⑤タイムアウト等の再送で二重配信を防ぐ。ArticleNotifications（FR-03-06）と二段で担保（NFR-07 冪等性）

制約: 通知フェーズでは LLM を一切呼ばない（要約は収集時に生成済み）。

原則（受信側の安全網）: 新着記事は LINE 送信の成否に関係なく必ずアプリ内（タイムライン）に入る。LINE 通知は補助的なプッシュであり、アプリが情報の正。LINE が失敗しても受信側が情報を取りこぼすことはない。受信側がアクションを要するのは「③ブロック/未追加」のみで、SC-09 の LINE 連携ステータス＋友だち追加案内で自己解決できる。

将来要件（Phase 6・VPS移行後）: ローカルでは通知は「PC 起動時に前回以降の新着をまとめて届ける」方式だが、VPS で常時稼働するようになった後は、決まった時間に収集結果を通知するスケジュール通知設定（時刻ベース通知。例: 毎朝8時に前日分をまとめて送る等、利用者ごとに通知時刻を設定）を提供する。§11 Phase 6「通知の時刻ベース化」に対応。

7. 外部インターフェース仕様

7.0 収集方式の考え方（RSS 優先の理由）

開発者向けの設計背景メモ（CLAUDE.md §0-3 の方針に基づき、選定理由を明文化）。

RSS とは

RSS（Really Simple Syndication） は、ニュースサイトやブログが「新着記事の一覧」を機械可読な XML 形式で配信する仕組み。人間向けの HTML ページとは別に、サイト自身が用意している「更新情報の配信口」である。1記事は以下のように、タイトル・URL・日付・要約・カテゴリがあらかじめタグで構造化されて届く。

<item>
  <title>○○フェア開催決定</title>
  <link>https://example.jp/news/123</link>
  <pubDate>2026-08-06</pubDate>
  <description>△△が開催される…</description>
  <category>イベント</category>
</item>

3段階の取得方式と、RSS を最優先にする理由

本アプリの心臓部は「複数サイトから最新情報を集めて構造化する」ことであり、取得方式を次の優先順で切り替える（FR-02-04）。

優先 方式 やること LLM コスト・手間
① RSS 配信口の XML をそのまま読む 不使用 最も軽い
② 専用パーサー HTML を解析してデータを取り出す 不使用 中（サイトごとに実装）
③ LLM 本文を Claude API に渡して構造化 使用 重い（課金あり）

RSS を最優先にするのは、本要件定義が掲げる制約に直結するため。

  1. コスト（NFR-06・§9）: RSS はタイトル・日付・カテゴリが最初から構造化されているため LLM を呼ぶ必要がない。LLM は呼ぶたびに課金されるので「RSS で取れるものは RSS で」が AI コスト月500円以内の鍵。
  2. 権利配慮（§9）: RSS はサイトが自ら公開している正規の配信窓口であり、HTML を力ずくで解析（スクレイピング）するより規約・権利面で安全。ポートフォリオ評価にも資する。
  3. 実装の軽さ・安定性: HTML はサイト改装でレイアウトが変わると壊れるが、RSS は形式が標準で安定。Phase 1（1テーマを日付順に並べる）を最短で回せる。第一陣3サイトを全て RSS で選んだのはこの理由。

RSS で不足する項目（要約・場所・発生日など）がある場合のみ、②専用パーサー → ③LLM の順で補完する。

Java での扱い

XML を自力パースはしない。ライブラリ ROME (rome-tools) が RSS/Atom の読み取りを担い、SyndFeedInput でパースした SyndFeed から各記事 SyndEntry を .getTitle() / .getLink() / .getPublishedDate() / .getDescription() 等のメソッドで取り出せる。フォーマット解釈はライブラリ任せにできる（「決まった形式のファイルを構造体に読み込む」感覚に近い）。HTTP 取得は Spring RestClient（＋Resilience4j）で行い、取得した本文を必要に応じて jsoup（専用パーサー）で解析する。

注記: 第一陣3サイトは「RSS を提供していると見られる」段階であり、その RSS が実際に生きているかは着手時の実地確認が必要（本セッションの環境では検証不可）。§7.1 の検証注記を参照。

robots.txt と遵守ゲート（権利配慮を仕組みで守る）

robots.txt とは、サイトが「自動プログラム（ボット）に許可する巡回範囲」を示す取り決めファイル（https://ホスト/robots.txt）。本アプリは複数サイトを自動巡回するボットそのものなので、これを尊重することが Web のマナーであり、規約・権利トラブルを避ける前提になる。技術的な鍵ではないが、無視は権利リスクになるため設計で守る。

例（抜粋）:

User-agent: *
Disallow: /admin/      ← ここ以下は取得しない
Allow:    /news/       ← ここは取得OK
Crawl-delay: 1         ← アクセスは1秒以上あけて

2段の遵守ゲート（効くタイミングが違う）:

ゲート 種別 いつ効くか 判定
規約ゲート 人手・情報源単位 その情報源を収集対象にするか（収集開始前） terms_reviewed=true の情報源だけ収集（未確認は集めない・FR-02-12）
robots ゲート 自動・ページ単位 各URLを取りに行く直前 robots.txt を判定し Disallow のパスはスキップ（FR-02-05）

robots ゲートの実装方針: - 取得直前に対象サイトの robots.txt を確認。相手・自分の負担を避けるため日次キャッシュ。 - robots.txt が無い/取得できない場合は慣例どおり許可扱い。ただし取得エラー（タイムアウト等）は安全側で当日スキップ。 - robots.txt のパースは自前実装せず定番ライブラリ（例: crawler-commons の SimpleRobotRules）に任せる（RSS を ROME に任せるのと同じ「決まった形式はライブラリ任せ」）。 - Crawl-delay があれば従う（＋同一ホスト間隔1秒以上・User-Agent にアプリ名＋連絡先）。

規約は機械では判定できないため人手確認（規約ゲート）、robots.txt は機械判定できるため自動（robots ゲート）、という役割分担にしている。

8.1 LINE 通知失敗の分類・対応（送信側）

判別は LINE API の HTTP ステータス＋例外種別で行う。常駐しないバッチのため「再送」は原則 次回PC起動時（同一実行内は秒単位の短いリトライのみ）。

分類（NotifyStatus） 判別 同一実行内リトライ 未通知を残す＝次回起動で再送 打ち切り 管理者向けメッセージ（例）
①TempError HTTP 5xx／接続断 ○（秒・指数バックオフ） ○ — 「LINE側の一時障害で送信できませんでした。次回に自動再送します」
②RateLimited HTTP 429 ○（Retry-Afterが短ければ従う） ○（長ければ待たず次回） — 「送信が集中し一時的に失敗。次回起動時に再送します」
③AuthFailed HTTP 401 ✗ ○（トークン修正後の次回に届く） 5日超過で GaveUp 「LINEトークンが無効です。設定を確認してください」
③Blocked push応答では判別困難（webhook要） ✗ ○（友だち追加後の次回に届く） 5日超過で GaveUp 「相手が未追加/ブロックの可能性。届いていません」
④FormatError HTTP 400＋詳細 ✗ ✗ ○ GaveUp（不具合） 「メッセージ形式エラー（不具合）。修正が必要です」
⑤Timeout 読み取りタイムアウト ✗ ○（冪等キー付き再送） — 「応答がなく送信状況が不明。冪等キーで二重を防ぎ再送します」
  • 再送する＝①②③⑤（未通知を残す）／打ち切り＝④、および③の5日超過（ArticleNotifications に GaveUp 記録）。
  • ⑤は「届いたか不明」のため冪等キー（FR-03-08）付きで再送し二重配信を防ぐ。
  • 受信側がアクションを要するのは③のみ → SC-09 の連携ステータス＋友だち追加案内で自己解決。それ以外は管理者/開発者が対処、または自動再送。

9. 制約・遵守事項（全工程で維持）

  • 権利: 記事本文をそのまま保存・表示しない（自作要約＋元URLのみ）。公式画像を自サーバー保存しない。ロゴ/ビジュアルを使わない。robots.txt を自動ゲートで尊重（FR-02-05）＋利用規約は人手確認ゲートで担保（terms_reviewed・FR-02-12）＝権利配慮を運用任せにせず仕組みで守る。スクレイピング禁止サイトは除外。→ README に明記。
  • コスト: LLM 呼び出しは収集時の構造化に限定。RSS で取れる情報源を優先。AI コストはユーザー数に比例させない。
  • 移行性: Windows 固有 API 不使用。パスは Path.of(...)。設定は全外部化。SQLite 不使用。文字コード UTF-8。バッチと Web は別プロセス。
  • 冪等性・UTC: §6・NFR-07/08 の通り。
