## 1. システム概要

アニメ・漫画などのテーマ（キーワード）を登録すると、関連する最新情報（グッズ・イベント・放送・コラボ等）を複数の情報源から自動収集し、発生日順の一覧で確認できる Web アプリケーション。お気に入り登録した対象に新着があれば LINE で通知する。

### 目的

アニメ・漫画のグッズ、ゲームセンターのプライズ、カプセルトイ（ガチャ）などの最新情報は複数の媒体に分散し追うのが大変で、人気商品はすぐ売り切れる。これらを1か所に自動集約し、見たいテーマの新着を効率よく把握できるようにする。あわせて、本プロジェクトは Java（Spring Boot + Vaadin Flow）習得を兼ねた転職用ポートフォリオとする。

> 補足: 収集は「PC 起動時にまとめて取得」方式であり、秒単位の即時アラートではない。目的は「1か所に集約して探す手間を減らす」こと。即時性は Phase 6（VPS・時刻ベース通知）で高める。

### 成功基準

1. 見たいテーマ（キーワード）を**登録**すると、システムが複数情報源から新着を自動収集し（**RSS を主とし、必要な箇所のみ LLM で構造化**）、発生日順の一覧・検索で確認できる。
2. お気に入り対象に新着が出たら **LINE に1通で通知**が届く。
3. **利用者2名それぞれのテーマ・お気に入り・既読・通知が互いに混ざらず**、画面・機能が一通り不具合なく動作する（協力者テストで確認）。
4. （コスト）AI 利用は**収集時の構造化のみ**で、月500円以内に収まる。

- 想定利用者: 2名（開発者本人＋協力者1名）
- 実行環境: 自宅 Windows PC（常時稼働しない）。バッチはタスクスケジューラでログオン時に起動。
- 将来: 転職活動開始時に VPS へ移設（Phase 6・実施確定）。
- 本プロジェクトは転職活動用ポートフォリオを兼ねる。

### 運用モデルに由来する前提

- 通知は時刻ベースではなく「PC 起動時に前回以降の新着をまとめて届ける」方式。
- 1日に複数回起動されうるため **冪等性の担保が必須**（重複登録・重複通知をしない、同日2回目以降は通知しない）。

### 対象範囲（スコープ）

本システムが「どこからどこまでを扱うか」の線引き。ここで範囲外を明示することで、後工程の設計・実装が意図から逸れないようにする（決定根拠は回答ログ Q13）。

**対象ドメイン**: アニメ・漫画に関する最新情報。種別はカテゴリ8区分（グッズ／アニメ〔放送〕／漫画／イベント／ゲーム／ゲームセンター／カプセルトイ／その他）で表現する。「コラボ」は横断的な情報で、実体に応じてイベント（コラボカフェ等）やグッズ（コラボ商品）に分類する。

**スコープ内（本プロジェクトで実現する）**:
- 情報の**収集**（複数情報源から自動収集）
- **一覧表示**（発生日順タイムライン・フィルタ・検索・未読既読）
- **LINE 通知**（お気に入り対象の新着）

**スコープ外（今回は実現しない）**:
- 記事本文／公式画像の保存・表示（自作要約＋元URLのみ）
- 利用者間の共有・コメント等のソーシャル機能
- 価格比較・在庫連携
- 購入・予約・SNS 投稿等のアクション連携

**将来の機能追加候補（今回は外すが拡張余地として記録）**:
- 在庫情報の取り込み
- 利用者数の拡大（3名以上）
- 汎用アグリゲーターとしての展開

**境界条件**:
- 言語＝日本語のみ／対象サイト＝国内のみ
- 利用者＝2名固定
- 対象期間＝直近**2年分**（DB 保持期間もこれに合わせる。NFR-05）。※前年と同時期・同種の新作（周年グッズ、季節イベント、シリーズ続編等）が出る傾向があり、前年同期と比較できるよう2年分を保持する

**拡張方針**: アニメ・漫画に**特化**した製品として提示する。テーマ／カテゴリ構造自体は特定ジャンルに依存しない汎用設計とし、将来の機能追加で汎用アグリゲーターとして見せられる余地を残す。

### 用語定義（ユビキタス言語）

言葉の意味を1つに固定する。要件・設計・実装・DB・画面で**同じ用語＝同じ意味**とし、対応するテーブル/enum/機能IDを併記して工程間のブレをなくす（トレーサビリティ §10）。

| 用語 | 定義 | 対応（テーブル/enum/ID） |
|---|---|---|
| 利用者（User） | 本システムを使う人。2名固定。ロールで admin/user を区別 | TBL-Users・enum UserRole |
| ロール（Role） | 利用者の権限区分。admin＝管理機能可／user＝一般 | Users.role・FR-07-04 |
| テーマ（Theme） | 利用者が登録する収集キーワード（例「呪術廻戦」）。利用者ごとに保持 | TBL-Themes・FR-01 |
| カテゴリ（Category） | 情報の種別。8区分（グッズ/アニメ/漫画/イベント/ゲーム/ゲームセンター/カプセルトイ/その他） | enum Category |
| 情報源（Source） | 記事を取得する対象サイト/フィード | TBL-Sources |
| robots.txt | サイトが「自動プログラム（ボット）に許可する巡回範囲」を示す取り決めファイル。うちは収集ボットとして取得直前にこれを尊重する（robots ゲート） | FR-02-05 |
| 遵守ゲート | 収集前後の2段の関所。**規約ゲート**（人手・情報源単位・`terms_reviewed`）と **robots ゲート**（自動・ページ単位・robots.txt）。両方を満たさない収集はしない | FR-02-05/12・TBL-Sources |
| 記事（Article） | 収集した最新情報1件。**自作要約＋メタ情報＋元URL**で構成し、本文・公式画像は保持しない | TBL-Articles・FR-02 |
| 発生日（EventDate） | 記事が表す事象の**代表日**。並び替え・期間フィルタのキー。曖昧な場合あり | Articles.event_date |
| 発生日原文（EventDateText） | 発生日の元の表記（例「9月上旬」「予約受付中」）。表示用 | Articles.event_date_text |
| 発生日精度（EventDatePrecision） | 発生日の確からしさ（Exact/Month/Season/Ongoing/Unknown） | enum EventDatePrecision |
| 発生日種別（EventDateKind） | 発生日が「何の日か」の種類（発売日/開催日/放送日/受付開始/その他）。表示ラベルと「発売日順」ソートに使う。※precision（確からしさ）とは別軸 | Articles.event_date_kind・enum EventDateKind |
| 収集（収集フェーズ） | 情報源から記事を取得し DB へ登録するバッチ処理。取得は RSS→専用パーサー→LLM の順 | FR-02・TBL-CrawlLogs |
| 通知（通知フェーズ） | お気に入り対象の新着を LINE で送る処理。収集とは別プロセスで **LLM 不使用** | FR-03 |
| LLM構造化 | 収集時に本文を Claude API でタイトル/日付/カテゴリ等へ構造化すること。**通知時は行わない** | FR-02-03・TBL-LlmUsageLogs |
| マッチ（ArticleThemeMatch） | 記事と有効テーマの突合結果（どの記事がどのテーマに該当するか） | TBL-ArticleThemeMatches・FR-02-10 |
| お気に入り（Favorite） | **通知対象**として登録したテーマ/情報源。通知 ON/OFF を持つ | TBL-FavoriteThemes/FavoriteSources・FR-05 |
| ブックマーク（Bookmark） | 「後で見る」で保存した個別記事。**通知対象ではない**。データパージの除外対象 | TBL-Bookmarks・FR-05-03 |
| 既読状態（ReadState） | 記事ごとの読んだ/未読の状態。利用者ごとに保持 | TBL-ReadStates・FR-04-04 |
| URLハッシュ（UrlHash） | 正規化した記事 URL のハッシュ。**重複記事の同一判定キー** | Articles.url_hash・FR-02-07/08 |
| 通数（Message count） | LINE 送信の消費単位＝**送信先ユーザー数 × 吹き出し数**。無料枠は月200通 | TBL-NotificationLogs |
| カルーセル | 複数記事を1吹き出しにまとめる LINE の Flex Message 形式 | FR-03-03 |
| 冪等性（Idempotency） | 複数回実行しても重複登録・重複通知が起きない性質。DB 制約で担保 | NFR-07・§6 |

> 用語の要注意点：**「お気に入り」＝通知する／「ブックマーク」＝通知しない（後で見るだけ）** は明確に別概念。**「テーマ」＝登録して収集させるもの／「検索」＝収集済みからの絞り込み（FR-04-03）** も別物。混同しないこと。

### ビジネスルール（計算・判定の決めごと）

| ルール | 内容 | 対応 |
|---|---|---|
| タイムライン整列キー | `COALESCE(event_date, created_at::date)`（発生日不明は収集日で代理し新着扱い） | FR-04-01 |
| 記事の同一判定 | `url_hash` 一致（正規化後）で重複とみなす。別サイトの同一情報はタイトル類似＋発生日でグルーピング | FR-02-08/09 |
| 取得優先順 | RSS → 専用パーサー → LLM（コスト・権利・安定性の順に有利） | FR-02-04 |
| 発生日種別の判定 | ①カテゴリ既定（グッズ/カプセルトイ/ゲーム/漫画→発売日、アニメ→放送日、イベント→開催日、ゲームセンター/その他→その他）→②原文キーワード補正（発売→発売日/開催→開催日/放送・配信→放送日/予約・受付→受付開始）→③LLMを呼ぶ記事のみ出力に種別を含める。**種別のために LLM を新規に呼ばない** | FR-02-06・EventDateKind |
| 発売日順ソート | 「発売日順」＝ `event_date_kind=発売日(1)` の記事を `event_date` で並べる（昇順で近い発売が上位）。「発生日順」は全種別横断で `COALESCE(event_date, created_at::date)` | FR-04-01 |
| 収集マナー | robots.txt 尊重／同一ホスト間隔1秒以上／User-Agent に連絡先／禁止サイト除外 | FR-02-05 |
| 通数カウント | 送信先ユーザー数 × 吹き出し数。1通に集約（カルーセル）。月200通接近で送信停止しアプリ内表示へ | FR-03-03/05 |
| 同日2回目の通知抑止 | `Users.last_notified_at` を JST 日付で判定（本日既送なら送らない） | FR-03-04 |
| LLMコスト集計 | `called_at` を JST 月に丸めて `SUM(est_cost_micro_jpy)`（表示時に円換算） | FR-06-06 |
| データ保持 | 記事2年（ただし Bookmark 済みは除外）、ログ1ヶ月で定期パージ | NFR-05 |
| 日時の扱い | UTC 保存（`timestamptz`）、表示直前に JST 変換 | NFR-08 |

## 3. 機能一覧

各機能に機能ID（`FR-xx-xx`）を付す。後工程（設計・実装・テスト）はこのIDを参照する。

### FR-01 テーマ管理

| ID | 機能 | 内容 |
|---|---|---|
| FR-01-01 | テーマ登録 | キーワードを登録する |
| FR-01-02 | テーマ編集 | キーワード・対象カテゴリ・有効フラグを編集 |
| FR-01-03 | テーマ削除 | テーマを削除（関連マッチは論理的に切り離す） |
| FR-01-04 | 収集対象カテゴリ指定 | テーマごとに収集対象カテゴリ（複数）を指定 |
| FR-01-05 | 収集有効/無効切替 | テーマ単位で収集の ON/OFF |

### FR-02 収集処理（バッチ・収集フェーズ）

| ID | 機能 | 内容 |
|---|---|---|
| FR-02-01 | RSS 取得 | RSS/Atom を直接パース（LLM 不使用） |
| FR-02-02 | 専用パーサー取得 | HTML 構造が安定した主要サイトを専用パーサーで取得（LLM 不使用） |
| FR-02-03 | LLM 構造化 | 上記以外は本文抽出→Claude API で構造化 |
| FR-02-04 | フォールバック制御 | 取得順は RSS → 専用パーサー → LLM |
| FR-02-05 | 収集マナー遵守 | **robots.txt 自動ゲート**：各URL取得の直前に対象サイトの robots.txt を取得（**日次キャッシュ**）し、Disallow のパスは取得せずスキップして `CrawlLogs` に記録。取得できない/無い場合は慣例どおり許可扱い、ただし**取得エラー（タイムアウト等）は安全側で当日スキップ**。robots.txt のパースは自前実装せず定番ライブラリ（例: crawler-commons）を利用。加えて同一ホスト間隔1秒以上、User-Agent にアプリ名＋連絡先を明記、Crawl-delay があれば従う |
| FR-02-12 | 規約遵守ゲート | 収集ループは **`is_active=true` かつ `terms_reviewed=true`** の情報源のみを対象にする。規約未確認（`terms_reviewed=false`）の情報源は登録できても**収集されない**（未確認は集めない、を仕組みで担保）。robots ゲート（FR-02-05）とは効くタイミングが異なる：規約＝情報源単位・収集開始前／robots＝ページ単位・取得直前 |
| FR-02-06 | 抽出項目マッピング | タイトル/カテゴリ/発生日(代表日・原文・精度)/**発生日種別(EventDateKind)**/場所/元URL/要約 を抽出（§7 参照）。種別は「①カテゴリ既定→②原文キーワード補正→③LLM出力（呼ぶ記事のみ）」で決定（ビジネスルール(§1)。種別のためだけに LLM を新規に呼ばない） |
| FR-02-07 | URL 正規化・ハッシュ | クエリ除去・リダイレクト解決後にハッシュ化 |
| FR-02-08 | 重複排除（一次） | UrlHash のユニーク制約で重複登録を防ぐ |
| FR-02-09 | 類似グルーピング | 別サイトの同一情報をタイトル類似度＋発生日でグルーピング |
| FR-02-10 | テーマ突合 | 収集記事を有効テーマのキーワードと突合し、マッチを永続化 |
| FR-02-11 | LLM予算ガード | LLM構造化（FR-02-03）を呼ぶ直前に、当月累計コスト（`LlmUsageLogs` 集計）が上限（安全マージン込み）に達していないか判定。達していれば **LLM を呼ばずスキップし RSS/専用パーサーの結果で登録**（収集は継続）。呼び出し後は `usage` からコストを算出し記録（NFR-06 ハードキャップ） |

### FR-03 通知処理（バッチ・通知フェーズ／収集と分離）

| ID | 機能 | 内容 |
|---|---|---|
| FR-03-01 | 未通知抽出 | 未通知フラグ方式で前回通知以降の新着を抽出 |
| FR-03-02 | お気に入り絞込 | お気に入り登録（通知ON）対象のみを通知対象にする |
| FR-03-03 | カルーセル集約 | 複数件を1通（Flex Message カルーセル）にまとめる。**カルーセルのバブル上限（LINE仕様上おおむね12件・着手時に公式確認）を超える分は切り詰め**、残りは「他◯件はアプリで確認」と促しアプリ内表示に委ねる（無料枠を余計に消費しないため分割送信はしない） |
| FR-03-04 | 同日2回目抑止 | 同日2回目以降の起動では送信しない |
| FR-03-05 | 通数管理 | 送信通数をカウントし、月間上限接近で送信を停止しアプリ内表示のみに切替 |
| FR-03-06 | 送信履歴記録 | 送信履歴を記録し再送を防止（`ArticleNotifications` で担保） |
| FR-03-07 | 送信失敗の分類・再送制御 | 送信失敗を `NotifyStatus`（§6 enum）に分類し `NotificationLogs` に記録。**再送方針**: ①一時障害/②レート制限＝同一実行内で短時間リトライ（Resilience4j・秒単位バックオフ）→ダメなら未通知を残し**次回起動時に再送**（常駐しないため「N分後」ではなく次回起動）。③認証失効/③ブロック＝自動リトライせず未通知を残す（原因解消後の次回起動で届く）が**5日超過で打ち切り**（アプリ内表示のみに切替）。④形式エラー＝**打ち切り**（同形式では必ず失敗＝不具合。スキップしログのみ）。⑤タイムアウト＝**冪等キー付きで再送**（届いたか不明なため二重送信を防ぎつつ次回起動で再送）。打ち切りは `ArticleNotifications` に「打ち切り」状態で記録し再送対象から外す。1利用者の失敗が他利用者の送信を止めない（NFR-10） |
| FR-03-08 | 二重送信防止（冪等キー） | LINE push の冪等キー（`X-Line-Retry-Key` 相当・着手時に公式確認）を用い、⑤タイムアウト等の再送で二重配信を防ぐ。`ArticleNotifications`（FR-03-06）と二段で担保（NFR-07 冪等性） |

> **制約**: 通知フェーズでは LLM を一切呼ばない（要約は収集時に生成済み）。

> **原則（受信側の安全網）**: 新着記事は LINE 送信の成否に関係なく必ずアプリ内（タイムライン）に入る。**LINE 通知は補助的なプッシュであり、アプリが情報の正**。LINE が失敗しても受信側が情報を取りこぼすことはない。受信側がアクションを要するのは「③ブロック/未追加」のみで、SC-09 の LINE 連携ステータス＋友だち追加案内で自己解決できる。

> **将来要件（Phase 6・VPS移行後）**: ローカルでは通知は「PC 起動時に前回以降の新着をまとめて届ける」方式だが、VPS で常時稼働するようになった後は、**決まった時間に収集結果を通知するスケジュール通知設定**（時刻ベース通知。例: 毎朝8時に前日分をまとめて送る等、利用者ごとに通知時刻を設定）を提供する。§11 Phase 6「通知の時刻ベース化」に対応。

## 6. データ設計（DDL レベル）

PostgreSQL 前提。日時は `timestamptz`（UTC 保存）。列挙型はアプリ側 enum に対応する `smallint`（コード値）で保持し、意味はコメントに明記する（JPA/Hibernate では `@Convert` で enum ↔ コード値を変換する `AttributeConverter` を用意する想定。※Hibernate 既定の `@Enumerated(ORDINAL)` は列挙順に暗黙依存し危険なため使わず、コード値を明示する Converter を挟む）。テーブルIDは `TBL-xxx`。

> 命名は PostgreSQL の慣習に合わせ snake_case を基本とする（JPA エンティティ側は camelCase、`@Column`/命名戦略でマッピング）。DDL は Flyway（`V1__*.sql`）で管理する。以下は論理定義。物理カラム名・制約名は詳細設計で確定する。

### 列挙値の定義

| enum | 値（コード: 意味） |
|---|---|
| Category | 1:グッズ / 2:アニメ / 3:漫画 / 4:イベント / 5:ゲーム / 6:ゲームセンター / 7:カプセルトイ(ガチャ) / 9:その他 |

## 7. 外部インターフェース仕様

### 7.0 収集方式の考え方（RSS 優先の理由）

> 開発者向けの設計背景メモ（CLAUDE.md §0-3 の方針に基づき、選定理由を明文化）。

#### RSS とは

**RSS（Really Simple Syndication）** は、ニュースサイトやブログが「新着記事の一覧」を機械可読な XML 形式で配信する仕組み。人間向けの HTML ページとは別に、サイト自身が用意している「更新情報の配信口」である。1記事は以下のように、タイトル・URL・日付・要約・カテゴリが**あらかじめタグで構造化**されて届く。

```xml
<item>
  <title>○○フェア開催決定</title>
  <link>https://example.jp/news/123</link>
  <pubDate>2026-08-06</pubDate>
  <description>△△が開催される…</description>
  <category>イベント</category>
</item>
```

#### 3段階の取得方式と、RSS を最優先にする理由

本アプリの心臓部は「複数サイトから最新情報を集めて構造化する」ことであり、取得方式を次の優先順で切り替える（FR-02-04）。

| 優先 | 方式 | やること | LLM | コスト・手間 |
|---|---|---|---|---|
| ① | **RSS** | 配信口の XML をそのまま読む | 不使用 | **最も軽い** |
| ② | 専用パーサー | HTML を解析してデータを取り出す | 不使用 | 中（サイトごとに実装） |
| ③ | LLM | 本文を Claude API に渡して構造化 | 使用 | 重い（課金あり） |

RSS を最優先にするのは、本要件定義が掲げる制約に直結するため。

1. **コスト（NFR-06・§9）**: RSS はタイトル・日付・カテゴリが最初から構造化されているため **LLM を呼ぶ必要がない**。LLM は呼ぶたびに課金されるので「RSS で取れるものは RSS で」が AI コスト月500円以内の鍵。
2. **権利配慮（§9）**: RSS はサイトが自ら公開している正規の配信窓口であり、HTML を力ずくで解析（スクレイピング）するより**規約・権利面で安全**。ポートフォリオ評価にも資する。
3. **実装の軽さ・安定性**: HTML はサイト改装でレイアウトが変わると壊れるが、RSS は形式が標準で安定。**Phase 1（1テーマを日付順に並べる）を最短で回せる**。第一陣3サイトを全て RSS で選んだのはこの理由。

RSS で不足する項目（要約・場所・発生日など）がある場合のみ、②専用パーサー → ③LLM の順で補完する。

#### Java での扱い

XML を自力パースはしない。ライブラリ **ROME (rome-tools)** が RSS/Atom の読み取りを担い、`SyndFeedInput` でパースした `SyndFeed` から各記事 `SyndEntry` を `.getTitle()` / `.getLink()` / `.getPublishedDate()` / `.getDescription()` 等のメソッドで取り出せる。フォーマット解釈はライブラリ任せにできる（「決まった形式のファイルを構造体に読み込む」感覚に近い）。HTTP 取得は Spring `RestClient`（＋Resilience4j）で行い、取得した本文を必要に応じて **jsoup**（専用パーサー）で解析する。

> 注記: 第一陣3サイトは「RSS を提供していると見られる」段階であり、**その RSS が実際に生きているかは着手時の実地確認が必要**（本セッションの環境では検証不可）。§7.1 の検証注記を参照。

#### robots.txt と遵守ゲート（権利配慮を仕組みで守る）

**robots.txt とは**、サイトが「自動プログラム（ボット）に許可する巡回範囲」を示す取り決めファイル（`https://ホスト/robots.txt`）。本アプリは複数サイトを自動巡回するボットそのものなので、これを尊重することが Web のマナーであり、規約・権利トラブルを避ける前提になる。技術的な鍵ではないが、無視は権利リスクになるため**設計で守る**。

例（抜粋）:

```
User-agent: *
Disallow: /admin/      ← ここ以下は取得しない
Allow:    /news/       ← ここは取得OK
Crawl-delay: 1         ← アクセスは1秒以上あけて
```

**2段の遵守ゲート**（効くタイミングが違う）:

| ゲート | 種別 | いつ効くか | 判定 |
|---|---|---|---|
| 規約ゲート | 人手・情報源単位 | その情報源を**収集対象にするか**（収集開始前） | `terms_reviewed=true` の情報源だけ収集（未確認は集めない・FR-02-12） |
| robots ゲート | 自動・ページ単位 | **各URLを取りに行く直前** | robots.txt を判定し Disallow のパスはスキップ（FR-02-05） |

**robots ゲートの実装方針**:
- 取得直前に対象サイトの robots.txt を確認。相手・自分の負担を避けるため**日次キャッシュ**。
- robots.txt が無い/取得できない場合は慣例どおり許可扱い。ただし**取得エラー（タイムアウト等）は安全側で当日スキップ**。
- robots.txt のパースは自前実装せず**定番ライブラリ（例: crawler-commons の `SimpleRobotRules`）**に任せる（RSS を ROME に任せるのと同じ「決まった形式はライブラリ任せ」）。
- Crawl-delay があれば従う（＋同一ホスト間隔1秒以上・User-Agent にアプリ名＋連絡先）。

> 規約は機械では判定できないため人手確認（規約ゲート）、robots.txt は機械判定できるため自動（robots ゲート）、という**役割分担**にしている。

### 7.1 収集対象（インバウンド取得）

| 情報源 | 取得方式 | RSS URL（着手時に実地確認） | 主なカバー範囲・備考 |
|---|---|---|---|
| MANTANWEB | RSS | `https://mantan-web.jp/rss/mantan.xml`（要確認） | アニメ/漫画/ゲーム/ラノベ。毎日新聞系の一次メディア |
| HOBBY Watch | RSS | インプレス系（正確なURLを着手時に特定） | フィギュア/グッズ/**プライズ（メーカー別：タイトー・セガ 等）**。グッズ・ゲームセンターの主軸 |
| Gamer | RSS | 着手時に特定（運営イード＝アニメ！アニメ！/インサイドと同基盤） | **アーケード・ゲームセンター**筐体・ロケテ・イベント/ゲーム |
| 電撃ホビーウェブ | RSS | 着手時に特定（`hobby.dengeki.com`。カプセルトイタグ `/tag/gatya/` あり） | **カプセルトイ（ガチャ）**・フィギュア/グッズ。KADOKAWA 運営のホビー総合メディア。**カプセルトイ枠を埋めるために第一陣に追加**（Q25） |

共通ルール: robots.txt 尊重、同一ホスト間隔1秒以上、User-Agent に連絡先を含める。RSS で不足する項目（要約・場所・発生日）は本文抽出→専用パーサー→LLM の順で補完。

将来Phase再検討（今回は不採用）:

### 7.2 Claude API（構造化・収集時のみ）

- 入力: 本文抽出テキスト（＋ページのタイトル/URL）
- 出力（JSON 構造化を要求）:
  - `title`（string）
  - `category`（Category enum のいずれか）
  - `event_date`（date or null）
  - `event_date_text`（string or null）
  - `event_date_precision`（EventDatePrecision）
  - `event_date_kind`（EventDateKind＝発売日/開催日/放送日/受付開始/その他。カテゴリ既定・原文から判断できる場合はそれを優先し、LLMは補助）
  - `location`（string or null）
  - `summary`（自作要約・本文転載しない）
- **モデル: Claude Sonnet**（正確なモデルID・単価・リクエスト形式は実装着手時に公式ドキュメントで確認。単価は `application.yml` に設定し `LlmUsageLogs` の概算コスト計算に用いる）。
- **コスト記録（案A）**: 各レスポンスの `usage`（`input_tokens` / `output_tokens`）を取得し、`単価×トークン数` で概算コストを算出して `LlmUsageLogs` に記録。**呼び出し前に当月累計を確認するハードキャップ（FR-02-11・NFR-06）**。組織のAdmin使用量/コストAPIは実請求との突合（任意）に留める。
- 呼び出しは公式 SDK **anthropic-sdk-java** を利用。差し替え可能にするため `LlmStructurer` インターフェース（Java の interface）を挟み、実装（Claude 版）を Spring の DI で注入する。予算判定は `LlmBudgetGuard` に集約し、収集サービスは LLM 呼び出し前に残予算を確認する。

### 7.3 LINE Messaging API（通知・アウトバウンド）

- 方式: push（友だち追加済みユーザーへ）、Flex Message カルーセルで複数件を1吹き出しに集約。
- 通数カウント: 「送信先ユーザー数 × 吹き出し数」。無料枠（コミュニケーションプラン）は月200通前提。上限接近時は送信停止しアプリ内表示に切替。
- 認証: チャネルアクセストークンは `application.yml` にはプレースホルダのみ置き、実値は環境変数 / `.env`（直書き禁止）。送信は公式 SDK **line-bot-sdk-java** を利用。
- 料金プラン・仕様は改定されるため実装着手時に公式ドキュメントを確認する。LINE Notify は 2025-03-31 終了済みのため Notify 前提記事は参照しない。

## 8. エラーハンドリング方針

| 場面 | 方針 |
|---|---|
| 情報源単位の失敗 | 1情報源で例外が出ても他情報源の収集を継続。失敗は `CrawlLogs` に記録（status=Failed/PartialError） |
| HTTP リトライ | Resilience4j でリトライ・タイムアウト・サーキットブレーカー。回数/間隔は設定外部化 |
| LLM 失敗 | 構造化失敗時は当該記事をスキップしログに残す（バッチ全体は止めない） |
| 重複登録 | UNIQUE 制約違反は正常系として扱い、当該記事を新規扱いしない |
| 通数上限到達 | 送信を停止し、アプリ内（ダッシュボード）に未通知として表示。ログに理由を記録 |
| LINE 通知失敗（分類・再送） | 失敗を `NotifyStatus` に分類し `NotificationLogs` に記録、SC-07/SC-08 に**分類別の管理者向けメッセージ**を表示（下表）。**新着は必ずアプリ内に残るためLINE失敗でも情報欠落しない**（受信側の安全網＝FR-04-06） |
| ログ方針 | ローカルファイル依存を避け DB（CrawlLogs/NotificationLogs/LlmUsageLogs）＋標準出力に寄せる。UTF-8 |
| 認証失敗（管理者PIN） | PIN 不一致はログイン画面にエラー表示して留める。**連続失敗（例: 5回）で当該管理者を数分ロック**し総当たりを抑止。一般利用者の選択ログインは失敗の概念なし。VPS移行時に本格認証へ |

### 8.1 LINE 通知失敗の分類・対応（送信側）

判別は LINE API の HTTP ステータス＋例外種別で行う。常駐しないバッチのため「再送」は原則 **次回PC起動時**（同一実行内は秒単位の短いリトライのみ）。

| 分類（NotifyStatus） | 判別 | 同一実行内リトライ | 未通知を残す＝次回起動で再送 | 打ち切り | 管理者向けメッセージ（例） |
|---|---|---|---|---|---|
| ①TempError | HTTP 5xx／接続断 | ○（秒・指数バックオフ） | ○ | — | 「LINE側の一時障害で送信できませんでした。次回に自動再送します」 |
| ②RateLimited | HTTP 429 | ○（`Retry-After`が短ければ従う） | ○（長ければ待たず次回） | — | 「送信が集中し一時的に失敗。次回起動時に再送します」 |
| ③AuthFailed | HTTP 401 | ✗ | ○（トークン修正後の次回に届く） | 5日超過で GaveUp | 「**LINEトークンが無効です。設定を確認してください**」 |
| ③Blocked | push応答では判別困難（webhook要） | ✗ | ○（友だち追加後の次回に届く） | 5日超過で GaveUp | 「相手が未追加/ブロックの可能性。届いていません」 |
| ④FormatError | HTTP 400＋詳細 | ✗ | ✗ | ○ GaveUp（不具合） | 「**メッセージ形式エラー（不具合）。修正が必要です**」 |
| ⑤Timeout | 読み取りタイムアウト | ✗ | ○（**冪等キー付き**再送） | — | 「応答がなく送信状況が不明。冪等キーで二重を防ぎ再送します」 |

- **再送する＝①②③⑤**（未通知を残す）／**打ち切り＝④、および③の5日超過**（`ArticleNotifications` に GaveUp 記録）。
- ⑤は「届いたか不明」のため冪等キー（FR-03-08）付きで再送し二重配信を防ぐ。
- 受信側がアクションを要するのは③のみ → SC-09 の連携ステータス＋友だち追加案内で自己解決。それ以外は管理者/開発者が対処、または自動再送。

## 9. 制約・遵守事項（全工程で維持）

- **権利**: 記事本文をそのまま保存・表示しない（自作要約＋元URLのみ）。公式画像を自サーバー保存しない。ロゴ/ビジュアルを使わない。**robots.txt を自動ゲートで尊重**（FR-02-05）＋**利用規約は人手確認ゲートで担保**（`terms_reviewed`・FR-02-12）＝権利配慮を運用任せにせず仕組みで守る。スクレイピング禁止サイトは除外。→ README に明記。
- **コスト**: LLM 呼び出しは収集時の構造化に限定。RSS で取れる情報源を優先。AI コストはユーザー数に比例させない。
- **移行性**: Windows 固有 API 不使用。パスは `Path.of(...)`。設定は全外部化。SQLite 不使用。文字コード UTF-8。バッチと Web は別プロセス。
- **冪等性・UTC**: §6・NFR-07/08 の通り。
