## 1. システム概要

アニメ・漫画などのテーマ（キーワード）を登録すると、関連する最新情報（グッズ・イベント・放送・コラボ等）を複数の情報源から自動収集し、発生日順の一覧で確認できる Web アプリケーション。お気に入り登録した対象に新着があれば LINE で通知する。

### 目的

アニメ・漫画のグッズ、ゲームセンターのプライズ、カプセルトイ（ガチャ）などの最新情報は複数の媒体に分散し追うのが大変で、人気商品はすぐ売り切れる。これらを1か所に自動集約し、見たいテーマの新着を効率よく把握できるようにする。あわせて、本プロジェクトは Java（Spring Boot + Vaadin Flow）習得を兼ねた転職用ポートフォリオとする。

> 補足: 収集は「PC 起動時にまとめて取得」方式であり、秒単位の即時アラートではない。目的は「1か所に集約して探す手間を減らす」こと。即時性は Phase 6（VPS・時刻ベース通知）で高める。

### 成功基準

1. 見たいテーマ（キーワード）を**登録**すると、システムが複数情報源から新着を自動収集し（**RSS を主とし、必要な箇所のみ LLM で構造化**）、発生日順の一覧・検索で確認できる。
2. お気に入り対象に新着が出たら **LINE に1通で通知**が届く。
3. **利用者2名それぞれのテーマ・お気に入り・既読・通知が互いに混ざらず**、画面・機能が一通り不具合なく動作する（協力者テストで確認）。
4. （コスト）AI 利用は**収集時の構造化のみ**で、月500円以内に収まる。

- 想定利用者: 2名（開発者本人＋協力者1名）
- 実行環境: 自宅 Windows PC（常時稼働しない）。バッチはタスクスケジューラでログオン時に起動。
- 将来: 転職活動開始時に VPS へ移設（Phase 6・実施確定）。
- 本プロジェクトは転職活動用ポートフォリオを兼ねる。

### 運用モデルに由来する前提

- 通知は時刻ベースではなく「PC 起動時に前回以降の新着をまとめて届ける」方式。
- 1日に複数回起動されうるため **冪等性の担保が必須**（重複登録・重複通知をしない、同日2回目以降は通知しない）。

### 対象範囲（スコープ）

本システムが「どこからどこまでを扱うか」の線引き。ここで範囲外を明示することで、後工程の設計・実装が意図から逸れないようにする（決定根拠は回答ログ Q13）。

**対象ドメイン**: アニメ・漫画に関する最新情報。種別はカテゴリ8区分（グッズ／アニメ〔放送〕／漫画／イベント／ゲーム／ゲームセンター／カプセルトイ／その他）で表現する。「コラボ」は横断的な情報で、実体に応じてイベント（コラボカフェ等）やグッズ（コラボ商品）に分類する。

**スコープ内（本プロジェクトで実現する）**:
- 情報の**収集**（複数情報源から自動収集）
- **一覧表示**（発生日順タイムライン・フィルタ・検索・未読既読）
- **LINE 通知**（お気に入り対象の新着）

**スコープ外（今回は実現しない）**:
- 記事本文／公式画像の保存・表示（自作要約＋元URLのみ）
- 利用者間の共有・コメント等のソーシャル機能
- 価格比較・在庫連携
- 購入・予約・SNS 投稿等のアクション連携

**将来の機能追加候補（今回は外すが拡張余地として記録）**:
- 在庫情報の取り込み
- 利用者数の拡大（3名以上）
- 汎用アグリゲーターとしての展開

**境界条件**:
- 言語＝日本語のみ／対象サイト＝国内のみ
- 利用者＝2名固定
- 対象期間＝直近**2年分**（DB 保持期間もこれに合わせる。NFR-05）。※前年と同時期・同種の新作（周年グッズ、季節イベント、シリーズ続編等）が出る傾向があり、前年同期と比較できるよう2年分を保持する

**拡張方針**: アニメ・漫画に**特化**した製品として提示する。テーマ／カテゴリ構造自体は特定ジャンルに依存しない汎用設計とし、将来の機能追加で汎用アグリゲーターとして見せられる余地を残す。

## 4. 非機能要件

| ID | 項目 | 要件 |
|---|---|---|
| NFR-01 | 利用者数 | 2名 |
| NFR-02 | 認証・認可 | **認証**: ローカルは利用者選択方式（一覧から自分をクリック。一般利用者はクレデンシャルなしの識別、**管理者のみ4桁PIN**をハッシュ照合）。**認可**: admin/user の2ロールを Spring Security で制御。VPS移行時(Phase 6)に全利用者を本格認証（パスワード/OAuth）へ差し替え、認可層は不変（authN/authZ 分離） |
| NFR-03 | バッチ所要時間 | 収集バッチは15分以内 |
| NFR-04 | 一覧応答 | 一覧表示は2秒以内 |
| NFR-05 | データ保持 | 記事**2年**、ログ1ヶ月（保持期間超過分は定期削除）。対象期間（直近2年分）と保持期間を一致させる（前年同期比較のため）。**ただし、いずれかの利用者が `Bookmarks` に保存済みの記事はパージ対象外**（「後で見る」を消さない）。パージ時は `Bookmarks` に存在しない・かつ `created_at` が2年超の記事のみ削除。関連する `ReadStates` / `ArticleThemeMatches` / `ArticleNotifications` は CASCADE で連動削除 |
| NFR-06 | AIコスト | 月500円以内を目標。LLM は収集時の構造化のみ |
| NFR-07 | 冪等性 | 複数回実行しても重複登録・重複通知が発生しない（DB制約で担保） |
| NFR-08 | 日時 | DB は `timestamptz`（UTC 保存）、Java 側は `Instant` で保持し表示直前に `ZoneId.of("Asia/Tokyo")` で JST 変換。ゾーンIDは一箇所に集約 |
| NFR-09 | 移行性 | VPS へ移設可能（OS非依存・別プロセス・設定外部化・SQLite不使用） |
| NFR-10 | 障害分離 | 1情報源の失敗が他情報源の処理を止めない |
| NFR-11 | 設定・秘密情報の外部化 | **12-factor 準拠で外部化する。機密（LINEトークン／Claude APIキー／DBパスワード等）は環境変数のみで注入し、`application.yml` はプレースホルダ `${...}` のみ・実値をリポジトリに置かない**（ローカル＝`.env`（gitignore）、VPS＝systemd `EnvironmentFile` 等）。**非機密の環境差分（DBホスト・ログレベル・User-Agent連絡先等）は Spring Profiles（`application-{profile}.yml`）で切替**。OS依存の資格情報ストアは NFR-09 に反するため使わない |
| NFR-12 | コンテナ化・デプロイ | **Docker を採用する**（Phase 0 で PostgreSQL は Docker Compose 済）。**開発中はアプリ本体（web/batch）を JAR / IDE で直接実行**し、PostgreSQL のみ Docker（反復速度優先）。**Phase 6 の VPS 移行時にアプリもコンテナ化**（マルチステージ `Dockerfile`）し、`docker compose` で web／batch／db を一括起動する。目的は **Windows→Linux の環境差異解消と環境再現性**（Docker は移行の必須条件ではないが、再現性とポートフォリオ価値のため採用）。秘密情報は compose の `env_file`／環境変数で注入し NFR-11 と整合させる。バッチは常駐せずワンショット実行のため、定期起動は運用要件（Phase 6＝cron/systemd timer, G1）と併せて設計する |

## 6. データ設計（DDL レベル）

PostgreSQL 前提。日時は `timestamptz`（UTC 保存）。列挙型はアプリ側 enum に対応する `smallint`（コード値）で保持し、意味はコメントに明記する（JPA/Hibernate では `@Convert` で enum ↔ コード値を変換する `AttributeConverter` を用意する想定。※Hibernate 既定の `@Enumerated(ORDINAL)` は列挙順に暗黙依存し危険なため使わず、コード値を明示する Converter を挟む）。テーブルIDは `TBL-xxx`。

> 命名は PostgreSQL の慣習に合わせ snake_case を基本とする（JPA エンティティ側は camelCase、`@Column`/命名戦略でマッピング）。DDL は Flyway（`V1__*.sql`）で管理する。以下は論理定義。物理カラム名・制約名は詳細設計で確定する。

## 7. 外部インターフェース仕様

### 7.0 収集方式の考え方（RSS 優先の理由）

> 開発者向けの設計背景メモ（CLAUDE.md §0-3 の方針に基づき、選定理由を明文化）。

#### RSS とは

**RSS（Really Simple Syndication）** は、ニュースサイトやブログが「新着記事の一覧」を機械可読な XML 形式で配信する仕組み。人間向けの HTML ページとは別に、サイト自身が用意している「更新情報の配信口」である。1記事は以下のように、タイトル・URL・日付・要約・カテゴリが**あらかじめタグで構造化**されて届く。

```xml
<item>
  <title>○○フェア開催決定</title>
  <link>https://example.jp/news/123</link>
  <pubDate>2026-08-06</pubDate>
  <description>△△が開催される…</description>
  <category>イベント</category>
</item>
```

#### 3段階の取得方式と、RSS を最優先にする理由

本アプリの心臓部は「複数サイトから最新情報を集めて構造化する」ことであり、取得方式を次の優先順で切り替える（FR-02-04）。

| 優先 | 方式 | やること | LLM | コスト・手間 |
|---|---|---|---|---|
| ① | **RSS** | 配信口の XML をそのまま読む | 不使用 | **最も軽い** |
| ② | 専用パーサー | HTML を解析してデータを取り出す | 不使用 | 中（サイトごとに実装） |
| ③ | LLM | 本文を Claude API に渡して構造化 | 使用 | 重い（課金あり） |

RSS を最優先にするのは、本要件定義が掲げる制約に直結するため。

1. **コスト（NFR-06・§9）**: RSS はタイトル・日付・カテゴリが最初から構造化されているため **LLM を呼ぶ必要がない**。LLM は呼ぶたびに課金されるので「RSS で取れるものは RSS で」が AI コスト月500円以内の鍵。
2. **権利配慮（§9）**: RSS はサイトが自ら公開している正規の配信窓口であり、HTML を力ずくで解析（スクレイピング）するより**規約・権利面で安全**。ポートフォリオ評価にも資する。
3. **実装の軽さ・安定性**: HTML はサイト改装でレイアウトが変わると壊れるが、RSS は形式が標準で安定。**Phase 1（1テーマを日付順に並べる）を最短で回せる**。第一陣3サイトを全て RSS で選んだのはこの理由。

RSS で不足する項目（要約・場所・発生日など）がある場合のみ、②専用パーサー → ③LLM の順で補完する。

#### Java での扱い

XML を自力パースはしない。ライブラリ **ROME (rome-tools)** が RSS/Atom の読み取りを担い、`SyndFeedInput` でパースした `SyndFeed` から各記事 `SyndEntry` を `.getTitle()` / `.getLink()` / `.getPublishedDate()` / `.getDescription()` 等のメソッドで取り出せる。フォーマット解釈はライブラリ任せにできる（「決まった形式のファイルを構造体に読み込む」感覚に近い）。HTTP 取得は Spring `RestClient`（＋Resilience4j）で行い、取得した本文を必要に応じて **jsoup**（専用パーサー）で解析する。

> 注記: 第一陣3サイトは「RSS を提供していると見られる」段階であり、**その RSS が実際に生きているかは着手時の実地確認が必要**（本セッションの環境では検証不可）。§7.1 の検証注記を参照。

### 7.1 収集対象（インバウンド取得）

| 情報源 | 取得方式 | RSS URL（着手時に実地確認） | 主なカバー範囲・備考 |

将来Phase再検討（今回は不採用）:
- タイトー/セガ/バンダイナムコ等 ゲームセンター公式のプライズ告知（RSS無し＋JS動的描画。一次情報だが専用パーサー＋規約確認前提。当面は HOBBY Watch 経由で代替）
- コミックナタリー（CDNがbotを遮断の疑い。採用時は規約確認＋許諾前提）
- アニメイトタイムズ（公式RSS無し。専用パーサー実装＋規約確認前提）

### 7.2 Claude API（構造化・収集時のみ）

- 入力: 本文抽出テキスト（＋ページのタイトル/URL）
- 出力（JSON 構造化を要求）:
  - `title`（string）
  - `category`（Category enum のいずれか）
  - `event_date`（date or null）
  - `event_date_text`（string or null）
  - `event_date_precision`（EventDatePrecision）
  - `location`（string or null）
  - `summary`（自作要約・本文転載しない）
- モデルID・リクエスト形式は実装着手時に公式ドキュメントで確認する。
- 呼び出しは公式 SDK **anthropic-sdk-java** を利用。差し替え可能にするため `LlmStructurer` インターフェース（Java の interface）を挟み、実装（Claude 版）を Spring の DI で注入する。

### 7.3 LINE Messaging API（通知・アウトバウンド）

- 方式: push（友だち追加済みユーザーへ）、Flex Message カルーセルで複数件を1吹き出しに集約。
- 通数カウント: 「送信先ユーザー数 × 吹き出し数」。無料枠（コミュニケーションプラン）は月200通前提。上限接近時は送信停止しアプリ内表示に切替。
- 認証: チャネルアクセストークンは `application.yml` にはプレースホルダのみ置き、実値は環境変数 / `.env`（直書き禁止）。送信は公式 SDK **line-bot-sdk-java** を利用。
- 料金プラン・仕様は改定されるため実装着手時に公式ドキュメントを確認する。LINE Notify は 2025-03-31 終了済みのため Notify 前提記事は参照しない。

## 8. エラーハンドリング方針

| 場面 | 方針 |
|---|---|
| 情報源単位の失敗 | 1情報源で例外が出ても他情報源の収集を継続。失敗は `CrawlLogs` に記録（status=Failed/PartialError） |
| HTTP リトライ | Resilience4j でリトライ・タイムアウト・サーキットブレーカー。回数/間隔は設定外部化 |
| LLM 失敗 | 構造化失敗時は当該記事をスキップしログに残す（バッチ全体は止めない） |
| 重複登録 | UNIQUE 制約違反は正常系として扱い、当該記事を新規扱いしない |
| 通数上限到達 | 送信を停止し、アプリ内（ダッシュボード）に未通知として表示。ログに理由を記録 |
| ログ方針 | ローカルファイル依存を避け DB（CrawlLogs/NotificationLogs）＋標準出力に寄せる。UTF-8 |
| 認証失敗（管理者PIN） | PIN 不一致はログイン画面にエラー表示して留める。**連続失敗（例: 5回）で当該管理者を数分ロック**し総当たりを抑止。一般利用者の選択ログインは失敗の概念なし。VPS移行時に本格認証へ |

## 9. 制約・遵守事項（全工程で維持）

- **権利**: 記事本文をそのまま保存・表示しない（自作要約＋元URLのみ）。公式画像を自サーバー保存しない。ロゴ/ビジュアルを使わない。robots.txt 尊重。スクレイピング禁止サイトは除外。→ README に明記。
- **コスト**: LLM 呼び出しは収集時の構造化に限定。RSS で取れる情報源を優先。AI コストはユーザー数に比例させない。
- **移行性**: Windows 固有 API 不使用。パスは `Path.of(...)`。設定は全外部化。SQLite 不使用。文字コード UTF-8。バッチと Web は別プロセス。
- **冪等性・UTC**: §6・NFR-07/08 の通り。
