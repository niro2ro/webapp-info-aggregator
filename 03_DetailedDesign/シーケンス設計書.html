1. 収集：1記事の登録（冪等・フォールバック）DD-SEQ-01

sequenceDiagram
    participant R as CollectionRunner
    participant CS as CollectionService
    participant RG as RobotsGate
    participant HF as HttpContentFetcher
    participant UN as UrlNormalizer/Hasher
    participant AR as ArticleRepository
    participant BG as LlmBudgetGuard
    participant LS as LlmStructurer
    participant AR2 as ArticleRepository
    R->>CS: run()
    CS->>RG: isAllowed(url)
    alt Disallow・取得エラー
        RG-->>CS: false
        CS->>CS: スキップし CrawlLogs 記録
    else Allow
        RG-->>CS: true
        CS->>HF: fetch(url)（RSS/HTML・間隔1秒・UA連絡先）
        HF-->>CS: RawItem
        CS->>UN: normalize→hash
        UN-->>CS: url_hash
        CS->>AR: existsByUrlHash(hash)
        alt 既存
            AR-->>CS: true → 登録しない（重複）
        else 新規
            AR-->>CS: false
            CS->>BG: hasBudget()
            alt 予算あり かつ 項目不足
                BG-->>CS: true
                CS->>LS: structure(extractedText)
                LS-->>CS: StructuredArticle + usage
                CS->>BG: recordUsage(usage)
            else 予算なし
                BG-->>CS: false（RSS/パーサー結果で登録）
            end
            CS->>AR2: save(Article)
            note over AR2: UNIQUE制約違反は DataIntegrityViolationException を握り重複扱い（冪等の最終防衛線）
            CS->>AR2: saveMatches(ArticleThemeMatch)
        end
    end

要点: 一次判定（existsByUrlHash）＋DB制約（UNIQUE）の二段で冪等。同時実行や取りこぼしがあっても最終防衛線で重複登録しない（DD-CLS-01/03/12〜22・BD-BATCH-C-06/07）。

2. 収集：情報源単位の障害分離 DD-SEQ-02

sequenceDiagram
    participant CS as CollectionService
    participant SRC as SourceRepository
    participant CL as CrawlLogRepository
    CS->>SRC: findActiveAndTermsReviewed()
    loop 情報源ごと（仮想スレッドで並行可）
        CS->>CS: collectFrom(source) を try/catch
        alt 成功
            CS->>CL: save(CrawlLog: Success, 件数)
        else 例外
            CS->>CL: save(CrawlLog: Failed, error)
            note over CS: 例外は握って次の情報源へ（1情報源の失敗が全体を止めない）
        end
    end

（NFR-10・BD-BATCH-C-01/14。並行化の理由は §5。）

3. 通知：未通知抽出→送信→結果記録 DD-SEQ-03

sequenceDiagram
    participant NR as NotificationRunner
    participant NS as NotificationService
    participant UR as UserRepository
    participant AN as ArticleNotificationRepository
    participant LN as LineNotifier
    participant NL as NotificationLogRepository
    NR->>NS: run()
    NS->>UR: findNotifiable()（notify_enabled かつ line_user_id）
    loop 利用者ごと（障害分離）
        NS->>UR: last_notified_at をJST日付で判定
        alt 本日既送
            NS->>NS: 送らず次へ
        else
            NS->>AN: 未通知の新着を抽出（行が無い記事）
            NS->>NS: お気に入り通知ON で絞込＋通数チェック
            alt 通数上限
                NS->>NS: 送信停止（アプリ内表示に委ねる）
            else
                NS->>NS: Flexカルーセルに集約（12件上限）＋冪等キー生成
                NS->>LN: push(bundle, idempotencyKey)
                alt 成功(2xx)
                    LN-->>NS: OK
                    NS->>AN: save(Delivered)・複合PKで重複通知防止
                    NS->>NL: save(通数)
                    NS->>UR: last_notified_at 更新
                else 失敗(分類)
                    LN-->>NS: NotifyStatus
                    alt 再送(①②③⑤)
                        NS->>NS: 行を作らず未通知のまま（次回起動で再送）
                    else 打ち切り(④/③5日超過)
                        NS->>AN: save(GaveUp)（再送対象外）
                    end
                end
            end
        end
    end

要点: 未通知＝ArticleNotifications に行が無い。成功/打ち切りでのみ行を作るため、複数回起動しても成功済みは再送されず失敗は次回届く（NFR-07・BD-BATCH-N・§8.1）。LLMは一切呼ばない。

4. 一覧表示（Web・SC-02）DD-SEQ-04

sequenceDiagram
    participant V as TimelineView
    participant TS as TimelineQueryService
    participant AR as ArticleRepository
    participant JF as JstFormatter
    V->>TS: query(criteria, pageable)（並び順/フィルタ/検索/ページ）
    TS->>AR: 整列キー COALESCE(event_date, created_at) ＋条件でページ取得
    AR-->>TS: Page<Article>
    TS->>JF: Instant→JST・種別ラベル付与
    JF-->>TS: List<TimelineItem>
    TS-->>V: Page<TimelineItem>
    V->>V: カード描画（画像枠なし・未読/未通知バッジ・外部リンクは新規タブ）

（NFR-04＝式インデックスで2秒以内。エンティティを画面に晒さず DTO 化・DD-CLS-28/31。）

5. 並行化の設計判断（仮想スレッド）DD-SEQ-05

  • 収集はI/Oバウンド（各サイトのHTTP待ちが支配的）。情報源ごとの取得をJava 21 の仮想スレッドで並行化すると、少ないコードで待ち時間を重ねられ 15分以内（NFR-03）に収まりやすい。
  • なぜ async/await 相当（CompletableFuture チェーン）を避けるか: 仮想スレッドなら「1情報源＝1スレッドで上から下に手続き的に書く」ままブロッキング呼び出しでよく、可読性が高い（Delphi の手続き的コードに近い書き味）。try/catch の障害分離もそのまま書ける。
  • ただし同一ホストへの間隔1秒以上（BD-IF-01-02）は守るため、同一ホストのリクエストは直列化（ホスト単位のガード）。DB書き込みはトランザクション境界を短く保つ（§データアクセス設計書）。
