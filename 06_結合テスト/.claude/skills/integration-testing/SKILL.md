# 結合テスト工程

モジュールを繋いだときに要件どおり動くかを、**実 DB（Docker の PostgreSQL）・実 I/F 相当**で検証する工程。単体テストで担保した部品が、繋いだ状態で破綻しないかを見る。

## 前提

- 単体テスト（`05_単体テスト/`）が完了していること。
- 対象機能が `04_実装/` に実装され、`docker compose up -d` で PostgreSQL が起動できること。
- 外部 API（Claude / LINE）は、原則テスト用チャネル/フェイクサーバまたはスタブで検証し、実送信は最小限かつ開発者の明示了承のもとで行う（誤送信・課金・通数消費を避ける）。

## 成果物（`06_結合テスト/` に作成）

| ファイル | 内容 |
|---|---|
| `結合テスト仕様書.md` | シナリオ一覧（`IT-001`…）。前提データ、手順、期待結果、対応要件ID（`FR-`）と画面ID（`SC-`） |
| `テストシナリオ.md` | 業務フロー単位の一連の操作（下記）を具体的な手順で記述 |
| `実施結果.md` | 実行日時・環境、シナリオごとの合否、スクショ/ログ等のエビデンス参照 |
| `既知不具合一覧.md` | 検出した不具合、重大度、対応要否、修正状況 |

## 検証する主要シナリオ

- **収集→保存→一覧表示**: RSS/専用パーサー/LLM の各経路で取得 → 正規化・重複排除 → DB 保存 → 一覧に日付順（発生日ベース、昇順/降順切替）で表示。フィルタ（テーマ/カテゴリ/期間/未読）・検索（部分一致）・未読既読が機能するか。
- **冪等性（最重要・実証必須）**: 収集バッチを**連続2回**実行 → 記事が重複登録されない。通知バッチを**同日2回**実行 → 2回目は送信0件。PC 起動シナリオ（1日複数回起動）を想定した反復実行。
- **収集→通知**: お気に入り対象に新着 → 未通知フラグ検出 → **1通にまとめて**（カルーセル）通知 → `ArticleNotifications` と `NotificationLogs` に記録。通知経路で LLM が呼ばれないこと。
- **通数上限**: 通数が上限に近づくと送信停止しアプリ内表示のみに切替。残量表示（管理画面）が正しいか。
- **障害分離**: 1情報源をわざと失敗（不正URL/タイムアウト）させても、他情報源の収集と一覧表示が継続し、`CrawlLogs` に失敗が記録される。
- **UTC/JST の一貫性**: バッチ保存（UTC）と画面表示（JST）が日付をまたぐケースでも一致。
- **管理機能**: バッチ手動実行、収集結果の確認・手動削除、通数残量表示、ログ閲覧。

## トレーサビリティ

各シナリオに要件ID・画面IDを紐づけ、`要件カバレッジ表.md` で「全要件がいずれかの結合テストで検証された」ことを示す。未カバー要件は理由（Phase 先送り等）を明記。

## チェックリスト

- [ ] 冪等性を「バッチ複数回実行」で実証したか（コードレビューでなく実行結果で）
- [ ] 収集の3経路（RSS/専用パーサー/LLM）がそれぞれ通ったか
- [ ] 通知が1通にまとまり、同日2回目が抑止されたか
- [ ] 障害分離が実際の失敗注入で確認できたか
- [ ] 全要件が結合テストでカバーされたか（カバレッジ表）
- [ ] 実 LINE 送信を伴う検証は開発者了承のもとで通数を消費しすぎないよう行ったか

## 位置づけ

Phase 3 完了後に**協力者による UI テスト**（Cloudflare Tunnel で一時公開）を行う想定。結合テストで機能面を固めてから協力者に触ってもらい、UI 指摘を回収する。

## 完了条件

全シナリオが合格（または不具合が既知不具合一覧で管理され、開発者が受容）し、要件カバレッジ表が埋まっていること。
