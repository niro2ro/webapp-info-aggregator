## 1. 背景と目的

### 背景
アニメ・漫画などのコンテンツに関する情報（グッズ発売、イベント開催、アニメ放送、コラボ企画など）は、公式サイト・SNS・グッズEC・イベント告知など複数の媒体に分散しており、個人が追い続けるのは手間がかかる。

### 目的
ユーザーがテーマ（作品名などのキーワード）を登録しておけば、関連する最新情報を自動収集し、日付順の一覧で確認できるようにする。お気に入り対象に新着があれば LINE で通知する。

### 副次的な目的
本プロジェクトは**転職活動用のポートフォリオ**を兼ねる。したがって以下を重視する。

- モダンな Java / Spring のスタックで実装すること
- 「なぜその設計にしたか」を説明できること（README に設計判断を記載）
- AI を使う箇所と使わない箇所の切り分けが明確であること
- 権利・コスト・冪等性への配慮が見えること

## 3. 利用者と運用形態

| 項目 | 内容 |
|---|---|
| 想定利用者数 | 2名（開発者本人＋1名） |
| 実行環境 | 自宅 Windows PC |
| DB | PostgreSQL（Docker コンテナでローカル起動） |
| バッチ起動方法 | タスクスケジューラ（ログオン時、遅延5分） |
| Web 画面の閲覧 | PC 起動中のみ localhost で閲覧 |
| 常時稼働 | しない |
| 協力者のテスト | Cloudflare Tunnel で一時的に外部公開 |

### 運用モデルから導かれる制約

PC 起動時にバッチが走るため、以下が仕様上の前提となる。

- **時刻ベースの通知ではない**。「毎朝8時に届く」ではなく「PC を立ち上げたら前回以降の新着がまとめて届く」
- PC を起動しない日は収集も通知も行われない
- 1日に複数回起動される可能性がある → **冪等性の担保が必須**
  - 同じ記事を重複登録しない
  - 同じ記事を重複通知しない
  - 同日2回目以降の起動では通知を送らない

### VPS 移行（実施が確定している）

**開発・テストは自宅 PC で行い、転職活動の開始時に VPS へ移設する。** これは「やるかもしれない」ではなく確定した計画である。移行は Phase 6 として実施する。

移行の目的は、転職活動中（3〜6ヶ月）にポートフォリオの URL を安定して提示できるようにすること。自宅 PC の常時稼働は電気代・Windows Update による再起動・停電などのリスクがあるため採用しない。

したがって、Phase 1 の時点から以下を守ること。**後付けでは直しにくい項目なので、設計段階で織り込む。**

| 項目 | 方針 |
|---|---|
| DB | 最初から PostgreSQL を使う。SQLite は使わない（移行時のデータ型・大文字小文字の差異でハマるため） |
| プロセス分離 | バッチと Web を別プロセスにする。Windows サービス化はしない（Linux で作り直しになる） |
| OS 依存 | Windows 固有の API を使わない。パスは `Path.of(...)` を使い `C:\` 等を書かない |
| 設定値 | 接続文字列・API キー・収集間隔などをすべて外部化する（`application.yml` にプレースホルダ → 実値は環境変数 / `.env`） |
| 日時 | **すべて UTC で DB に保存し、表示時にローカル時刻へ変換する。** Java 側は `Instant`（UTC）で保持し、表示直前に `ZoneId.of("Asia/Tokyo")` で JST 変換。ゾーンIDは一箇所に集約する（`ZoneId` は IANA tz 名で全OS共通のため .NET のような識別子差異は無いが、ハードコード分散は避ける） |
| ファイル出力 | ログを含めローカルファイルへの依存を避け、DB または標準出力に寄せる |
| 文字コード | UTF-8 で統一する |

### 移行時に発生する作業（Phase 6 で実施）

| 項目 | 内容 |
|---|---|
| DB 移行 | `pg_dump` / `pg_restore` でデータを移送。スキーマは同一のため変換は不要 |
| バッチ起動 | タスクスケジューラ → cron または systemd timer に置き換え |
| 通知トリガー | 「PC 起動時」から「毎朝定時」に変更。§4.3 の未通知フラグ方式のままで対応できる設計にしておくこと |
| 設定管理 | ローカルは `.env` / 環境変数 → 本番は環境変数・Secret 管理 |
| HTTPS | Let's Encrypt で証明書を取得 |
| 認証 | 外部公開に伴い認証を必須化する。デモ用の読み取り専用モードの要否を検討する |
| 死活監視 | UptimeRobot 等で監視し、停止時に通知が来るようにする |

Claude Code は移行時、本節を参照して手順書を作成すること。

## 4. 機能要件

### 4.1 テーマ管理
- テーマ（キーワード）の登録・編集・削除
- テーマごとの収集対象カテゴリ指定（グッズ / アニメ / 漫画 / イベント / ゲーム）
- 収集の有効・無効切り替え

### 4.2 収集処理（バッチ）

情報源の種別に応じて取得方式を切り替える。**すべてを LLM で処理しないこと。**

| 情報源の種別 | 取得方式 | LLM |
|---|---|---|
| RSS / Atom が提供されている | 直接パース | 使わない |
| HTML 構造が安定している主要サイト | 専用パーサー | 使わない |
| 上記以外 | 本文抽出 → LLM で構造化 | 使う |

- 取得順は「RSS → 専用パーサー → LLM」のフォールバック構成とする
- robots.txt を尊重する
- 同一ホストへのリクエスト間隔は1秒以上空ける
- User-Agent に連絡先を含める

**抽出項目**

| 項目 | 説明 |
|---|---|
| タイトル | 情報の見出し |
| カテゴリ | グッズ / アニメ / 漫画 / イベント / ゲーム / その他 |
| 発生日 | 発売日・開催日など。表記ゆれ（「9月上旬」「秋頃」）の扱いを要件定義で決める |
| 場所 | イベントの場合のみ |
| 元URL | 必須 |
| 要約 | 自作の要約。本文は保存しない |

**重複排除**

1. URL 正規化（クエリパラメータ除去、リダイレクト解決）してハッシュ化
2. ハッシュの一致で一次判定（DB のユニーク制約で担保）
3. 別サイトの同一情報はタイトル類似度＋発生日でグルーピング

### 4.3 通知処理（バッチ）

**収集処理とは別プロセス、または明確に分離されたステップとして実装すること。**

理由：収集は時間がかかり失敗もありうるが、通知は既存データだけで完結できるため。

- 未通知フラグ方式で、前回通知以降の新着をすべて拾う
- お気に入り登録された対象のみを通知対象とする
- **1通に複数件をまとめる**（Flex Message のカルーセル）
- 同日2回目以降の起動では送信しない
- 送信通数をカウントし、月間上限に近づいたら送信を停止する
- 送信履歴を記録し、再送を防止する

**この処理で LLM は使わないこと。** 要約は収集時点で生成済みであり、通知時に再生成する必要はない。通知時に LLM を呼ぶとユーザー数×通知回数だけコストが増えるため、明確に避ける。

### 4.4 一覧表示（Web）
- 日付順タイムライン（発生日ベース、昇順・降順切替）
- フィルタ：テーマ / カテゴリ / 期間 / 未読
- 検索：タイトル・要約の部分一致
- 未読・既読管理
- 元記事へのリンク

### 4.5 お気に入り
- テーマ単位のお気に入り
- 情報源単位のお気に入り
- 個別記事のブックマーク（後で見る用。通知対象ではない）
- お気に入りごとの通知 ON / OFF

### 4.6 管理機能
- 情報源マスタの登録（URL、取得方式、有効フラグ）
- バッチの手動実行
- 収集結果の確認・手動削除
- LINE 送信通数の残量表示
- 実行ログの閲覧

| テーブル | 主な項目 |
|---|---|

| `NotificationLogs` | UserId, SentAt, ArticleCount, MessageCount |
| `CrawlLogs` | SourceId, StartedAt, ItemCount, Status, ErrorMessage |

**冪等性の担保方法**

- `Articles.UrlHash` にユニーク制約を張り、重複登録を DB レベルで防ぐ
- `ArticleNotifications` の (UserId, ArticleId) で重複通知を防ぐ
- アプリ側のチェックだけに頼らないこと

## 8. LINE Messaging API の制約

**重要：無料枠が厳しい。設計に直接影響する。**

- LINE Notify は 2025年3月31日にサービス終了済み。ネット上の解説記事の多くは Notify 前提なので注意すること
- 無料プラン（コミュニケーションプラン）の月間無料メッセージ通数は 200通
- カウント方法は「送信先ユーザー数 × 吹き出し数」
  - 同じ内容でも2人に送れば2通
  - 1回の送信で吹き出しを2つ使えば2通
- 有料プランは月額5,000円から

**料金プランは改定されることがあるため、着手時点で LINE 公式ドキュメントを確認すること。**

### 設計への反映

- 新着1件ごとに通知せず、**必ず1通にまとめる**（カルーセルで複数件を1吹き出しに格納）
- 利用者2名で日1通なら月60通程度。無料枠に収まる
- 通数カウントを DB に記録し、上限接近時は送信を停止してアプリ内表示のみに切り替える

### セットアップ手順の概要

1. LINE 公式アカウントを作成
2. Messaging API を有効化
3. LINE Developers コンソールでチャネルアクセストークン（長期）を発行
4. 利用者が公式アカウントを友だち追加する（**これがないと push できない**）
5. ユーザーID を取得して DB に登録

アクセストークンは環境変数 / `.env`（`application.yml` はプレースホルダのみ）で管理し、**ソースコードやリポジトリに含めない**。

## 9. 制約・遵守事項

### 権利関係
- **記事本文をそのまま保存・表示しない**。自作の要約と元記事へのリンクのみ
- 公式画像を自サーバーに保存して表示しない
- 作品名・キャラクター名への言及は問題ないが、ロゴやビジュアルの使用は避ける
- robots.txt を尊重する
- 収集対象サイトの利用規約を確認し、スクレイピングが禁止されている場合は情報源から除外する

これらの配慮は README に明記すること。ポートフォリオとしての評価に直結する。

### コスト
- LLM の呼び出しは収集時の構造化に限定する
- AI コストは「情報源の数 × 更新頻度」に比例し、ユーザー数には比例しない構造とする
- RSS で取得できる情報源を優先し、LLM の使用を減らす

## 10. 決定が必要な事項

Claude Code は要件定義に入る前に、以下を開発者に確認すること。

### 10.1 対象範囲
- テーマはアニメ・漫画作品に限定するか、汎用（バンド、ゲーム、企業など）にするか
- カテゴリの区分は現在の5分類（グッズ / アニメ / 漫画 / イベント / ゲーム）でよいか

### 10.2 情報源
- 最初に実装する情報源3つを具体的に決める
- 各情報源が RSS を提供しているかを調査する（実装量が大きく変わる）
- 利用規約上、収集が許容されるかを確認する

### 10.3 技術選定
- **DB は PostgreSQL で確定。この点は質問不要。** Docker でローカル起動する
- Web 構成（Vaadin Flow か、Thymeleaf + htmx か、REST API + 別フロントか）
- LLM は Claude API でよいか
- 日本語の全文検索が必要か（必要なら pg_bigm または pg_trgm の導入を検討）

### 10.4 日付の表記ゆれの扱い
「2026年9月上旬発売予定」「秋頃」「予約受付中」といった曖昧な日付をどう格納するか。
確定日と曖昧表現を別カラムで持つか、精度フラグを持たせるか。**ここは早めに決めないと後で辛くなる。**

## 11. 実装フェーズ

要件定義完了後、以下の順で進める。各フェーズが完成してから次に進むこと。

| Phase | 内容 | 完成条件 | 実施時期 |
|---|---|---|---|
| 0 | Docker Compose で PostgreSQL 起動、Spring Boot + JPA 接続確認、Flyway 実行 | Flyway マイグレーションが通る | 着手時 |
| 1 | DB 設計、テーマ登録、RSS 収集、一覧表示 | 1テーマ分の情報が日付順に並ぶ | |
| 2 | LLM による構造化、重複排除、情報源追加 | 3ソース以上から収集できる | |
| 3 | お気に入り、未読管理、フィルタ、検索 | 日常的に使える | |
| — | **協力者によるテスト**（Cloudflare Tunnel で一時公開） | UI の指摘を回収する | Phase 3 完了後 |
| 4 | LINE 通知、冪等性の担保 | PC 起動時に1通届く | |
| 5 | タスクスケジューラ登録、管理画面、ログ | 自宅 PC で自動で回る | |

協力者によるテストは Phase 3 完了後に行う。通知まで作り込んでからだと、UI の根本的な指摘を受けたときの手戻りが大きくなるため。
