1スコープ・目的

項目決めたことなぜこの設計にしたか
★目的・提供価値 アニメ・漫画のグッズ／プライズ／カプセルトイ等、複数媒体に分散する最新情報を1か所に自動集約し、テーマの新着を効率よく把握する。Java 習得を兼ねた転職用ポートフォリオ。 人気商品はすぐ売り切れ、情報が媒体ごとに散る＝「探す手間」が課題。価値の核はそこ。即時アラートではなく「集約して探す手間を減らす」と正直に線引きした（即時性は Phase 6 で後追い）。
★対象範囲 / スコープ外 内＝収集・一覧表示・LINE通知。外＝本文/公式画像の保存、共有・コメント等ソーシャル、価格比較・在庫連携、購入・予約・SNS投稿。 「あえて作らないもの」を明示し、後工程の実装が意図から逸れないようにする。本文非保存はスコープ判断であり権利配慮（§9）とも一致。将来候補（在庫・3名以上・汎用化）は別枠で記録。
想定利用者・利用シーン 2名（本人＋協力者1名）。自宅 Windows PC で常時稼働せず、ログオン時にバッチ起動。NFR-01 小規模・非常時稼働という前提が、後述の冪等性必須・LINE無料枠・コスト設計すべての土台。ここを固定しないと非機能が決まらない。
★成功基準 ①登録→自動収集（RSS主・必要箇所のみLLM）→一覧・検索 ②お気に入り新着をLINEに1通 ③2名のデータが混ざらず一通り動作 ④AIは収集時のみ・月500円以内。 検証できる形に落とした。この4基準から必要機能を洗い出して既存FRと照合（トップダウン照合＝回答ログ Q15）し、抜けていた4点（定期実行/LINE連携/LLMコスト可視化/利用者管理）を補完した。

2機能

項目決めたことなぜこの設計にしたか
機能一覧 FR-01テーマ管理 / FR-02収集 / FR-03通知 / FR-04一覧表示 / FR-05お気に入り / FR-06管理 / FR-07認証・利用者。 成功基準①〜④を過不足なく満たす単位に分割。収集(FR-02)と通知(FR-03)を別機能・別バッチに分離したのは、1情報源の失敗や再実行が通知に波及しないようにするため。
★優先順位（Must/Should/Could） Must（核）：テーマ管理・収集(RSS/重複排除)・一覧・検索・お気に入り・LINE通知・認証/認可。Should：LLM構造化/専用パーサー/類似グルーピング・フィルタ/未読既読・管理機能・LLMコスト可視化。Could：ブックマーク・収集結果削除。※重要度(MoSCoW)と着手順(Phase)は別軸。 §3.1 個人開発かつ学習兼のため「最短で動くものから」。まずRSSだけで骨格（1テーマが日付順に並ぶ）を通し、LLM・重複排除・通知は後追い。検索は成功基準①に明記のMustで、Phase 2に前倒し。通知・認証はMustだが着手は後段（Phase 4-5）＝重要度と順番を分けて管理。
トリガー・入力・出力 収集＝スケジューラ/手動起動→情報源→記事DB。通知＝バッチ→お気に入りの新着→LINE push。閲覧＝Web操作→画面。 起点が「PC起動時の一括バッチ」なので、入力は時刻ではなく「前回以降の新着」。この非同期・まとめ処理という性質が冪等性要件を生む。
★やらないこと（境界） 記事本文の転載はしない／通知フェーズではLLMを一切呼ばない／収集はログイン必須・robots禁止サイトに入らない／検索は部分一致まで（意味検索はしない）。通知はローカルではPC起動時まとめ（即時アラートではない）。 §3.2 機能の境界を明示してスコープクリープを防ぐ。通知時LLM不使用は「AIコストを利用者数に比例させない」設計判断の帰結。※将来（Phase 6・VPS移行後）：常時稼働になったら決まった時間に収集結果を通知するスケジュール通知設定（時刻ベース通知）を提供する——ローカルの「起動時まとめ」から公開運用の「定時通知」へ、段階的に即時性を高める設計。

3非機能要件（品質特性）

項目決めたことなぜこの設計にしたか
性能 収集バッチ15分以内 NFR-03／一覧表示2秒以内 NFR-04。同時実行は2名で軽微。 利用者2名・非常時稼働なので過大な性能目標は不要。全文検索は pg_trgm＋GINインデックスで2秒目標を担保（D7）。
可用性・稼働条件 常時稼働しない。PC起動時にまとめて収集・通知。1日複数回起動されうる。 この稼働モデルが冪等性を必須にする直接の理由。同じ記事を重複登録・重複通知しない、同日2回目以降は通知しない、を設計前提に据えた。
データ量・保持期間 記事2年・ログ1ヶ月で定期パージ NFR-05。ただしブックマーク済み記事は対象外。 2年は前年同期比較（周年グッズ・季節イベント・続編）ができるようにするドメイン判断。対象期間と保持期間を一致させた。
★セキュリティ・認証/認可 認証＝ローカルは利用者選択方式（一覧から自分をクリック）。一般利用者は鍵なし（識別）、管理者のみ4桁PIN（ハッシュ照合・連続失敗ロック）。認可＝admin/user の2ロールを Spring Security で制御し、管理系（情報源マスタ／管理ダッシュボード＝LLMコスト含む／実行ログ／利用者管理）は admin 限定。NFR-02 FR-07 自宅PC・信頼できる2名という脅威モデルでは、日常操作は鍵なしのクリックログインで手間を最小化して合理的。ただし鍵なしだと管理者を誰でも選べるため、管理者ロールにだけ最小の鍵(PIN)を課してLLMコスト等の管理機能を保護。authN(認証方式)とauthZ(ロール制御)を分離し、VPS(Phase 6)では認証方式だけを本格認証へ差し替え、認可層は不変にする——この分離自体が「認証と認可を理解している」説明ネタになる（"簡易認証"の曖昧語は廃止）。
★拡張性・移行性 OS非依存・Web/バッチ別プロセス・設定全外部化・SQLite不使用・UTF-8統一 NFR-09。日時はUTC保存/JST表示 NFR-08。秘密情報は環境変数で外部化（案A・12-factor）：機密（LINEトークン/Claudeキー/DBパスワード）は環境変数のみ、application.ymlはプレースホルダのみでリポジトリに実値を置かない。非機密の環境差分はSpring Profilesで切替 NFR-11。コンテナ化＝Docker採用：開発中はアプリを直実行＋DBのみDocker、Phase 6のVPS移行時にアプリもDocker化（マルチステージDockerfile＋compose一括起動） NFR-12。 VPS移行が確定済みの将来。移行を阻害する制約（Windows固有API・ローカルパス・時刻ゾーン散在）は後付けで直しにくいので最初から守る。秘密情報は案A（環境変数）を採用＝手間最小で移行性・安全性を両立し説明も容易。※将来の高度化余地：Jasypt等で暗号化した秘密をリポジトリにコミットする案C（秘密の履歴管理・より一段深い見せ方）も選択肢で、必要になれば後日検討してよい（マスターキー管理は結局env方式と同様に必要）。Dockerは移行の必須ではない（JARはOS非依存）が、Windows→Linuxの環境差異を消して移行を安全化し、ポートフォリオでDockerスキルを示せるため採用。開発の反復速度を守るため導入は成果物として残るPhase 6とした。
コスト上限 AI 月500円以内目標 NFR-06／LINE無料枠 月200通前提。 この2つの上限が「RSS優先・LLMは補完のみ」「通知は1通に集約」という設計の駆動力。コスト設計を非機能として明示し、可視化機能(FR-06-06)で検証可能にした。

💡 補足解説：Docker とは（未経験者向け）

ひとことで：アプリを「動く環境ごと」1つの箱に固めて、どのマシンでも同じに動かす道具。「自分のPCでは動くのに別サーバーでは動かない」という環境差異をなくす（Delphi/ERP でいう「客先環境を揃える苦労」を消す）。

仮想マシン(VM)との違い：VM は OS 丸ごとを仮想化して重い。コンテナは OS の核(カーネル)をホストと共有し、アプリと依存だけを隔離するので軽い・秒で起動（例え：VM＝一戸建てを各自建てる／コンテナ＝1棟のマンションの各部屋）。

覚える用語は4つ：

イメージ(image)アプリ一式を固めた“型”。不変 ＝ プログラムのクラスにあたる
コンテナ(container)イメージを起動した“実働の1つ” ＝ インスタンスにあたる
Dockerfileイメージの作り方レシピ（ビルド手順書）
レジストリイメージを配布する倉庫（Docker Hub 等。Maven Central のイメージ版）

複数の箱をまとめて起動する指揮書が Docker Compose。消えては困るデータ（DBの中身）は「ボリューム」という外部領域に逃がす。

この案件では既に使用中：Phase 0 で PostgreSQL を Docker Compose で起動している（イメージ取得→コンテナ起動→データはボリューム保存）。④の論点は「DBだけでなくアプリ(Web/バッチ)も箱に入れるか」の一点で、開発は直実行／Phase 6 VPS でアプリもDocker化と決定（NFR-12・項目3参照）。

4データ

項目決めたことなぜこの設計にしたか
管理対象（エンティティ） Users / Themes / ThemeCategories / Sources / Articles / ArticleThemeMatches / FavoriteThemes / FavoriteSources / Bookmarks / ReadStates / ArticleNotifications / NotificationLogs / CrawlLogs / LlmUsageLogs。 機能から素直に導出。お気に入りはテーマ用/情報源用にテーブル分割（当初のポリモーフィック1テーブル案を却下）。FKで参照整合性をDBに担保させるため。
データ項目・型・制約 DDLレベルで定義。列挙型は smallint コード値＋コメントで保持。日時は timestamptz。 Hibernate既定の @Enumerated(ORDINAL) は列挙の並び順に暗黙依存し危険なので使わず、コード値を明示するConverterを挟む。値の追加でスキーマ変更が不要になる利点も。
★一意性・重複の定義 「同じ記事」＝ Articles.url_hash が同一（URL正規化＝クエリ除去・リダイレクト解決後にハッシュ化）で UNIQUE。別サイトの同一情報はタイトル類似度＋発生日でグルーピング。 冪等性の核。何をもって重複とするかを先に固定しないと、多重起動で重複登録・重複通知が起きる。アプリ判定に頼らずDBのUNIQUE制約を最終防衛線にする。
★保持・削除ポリシー 記事は2年超で定期パージ。ただし誰かが Bookmarks 済みの記事は消さない（「後で見る」を保護）。 保持と利用者の意図が衝突する箇所。単純な期限削除だと保存済みが消える事故が起きるため、パージ条件にブックマーク除外を明示した。
整合性ルール（親子・削除連動） Articles/Users/Themes配下は ON DELETE CASCADE。Sources配下のみ RESTRICT。 子データの孤児化を防ぐためCASCADE。ただし収集済み記事を持つ情報源の誤削除は事故になるのでSourcesだけRESTRICTにし、無効化は is_active=false で行う。

5外部インターフェース

項目決めたことなぜこの設計にしたか
連携先 収集元（RSS/HTML）、Claude API（構造化）、LINE Messaging API（通知）。 収集は取得、Claudeは整形、LINEは配信と役割が明確。LLMは差し替え可能にするため LlmStructurer インターフェースで抽象化しDI注入。
方式・頻度・入出力 RSSは ROME、HTTPは RestClient＋Resilience4j、必要時 jsoup。Claudeは本文→JSON構造化。LINEは push＋Flexカルーセル。 取得はRSS→専用パーサー→LLMの3段フォールバック FR-02-04。RSSは最初から構造化済みで安定・低コスト・権利面で安全なので最優先。
★外部制約への対応 LINE無料枠200通＝1通に集約（カルーセル）＋通数をDB記録し上限接近で送信停止しアプリ内表示へ。LLM課金＝RSS優先で呼び出しを減らし、月500円をハードキャップ：`usage`(トークン数)×単価で自前計算し（案A）、上限到達でLLM構造化を停止しRSSで収集継続。モデルはSonnet（≒¥1.6/記事・月約300記事）。robots.txt尊重・間隔1秒・UAに連絡先・禁止サイト除外。 無料枠/課金/規約という外部の有限資源とルールが設計を縛る。LINEは吹き出しを増やさない集約が効く。LLMコストは「呼ぶ直前に当月累計を見て止める」ハードキャップで月500円を“守れる”設計に。組織のAdminコストAPIは集計遅延・組織単位で判定に不適なため、各レスポンスのusageを自前集計する案Aを採用。権利遵守はポートフォリオ評価にも資する。
連携障害時の扱い 情報源単位で失敗を分離（1失敗で全体を止めない）。Resilience4jでリトライ/タイムアウト/CB。LLM失敗は当該記事スキップ。 複数外部依存があるため1点の障害を全体障害にしないのが方針。失敗は握りつぶさず CrawlLogs に記録して可視化。

7制約・前提

項目決めたことなぜこの設計にしたか
★技術前提 Java 21 / Spring Boot 3.x / Vaadin Flow / PostgreSQL（確定 D8）/ Flyway / Spring Data JPA。 当初の .NET(Blazor) からJava学習を兼ねたポートフォリオへピボット（回答ログ Q12）。機能・非機能・画面・データ設計は言語非依存で不変、技術構成のみ差し替え。DBは一貫してPostgreSQL。
★法的・権利・コンプラ 記事本文/公式画像を保存・表示しない（自作要約＋元URLのみ）。ロゴ/ビジュアル不使用。robots.txt尊重・スクレイピング禁止サイト除外。READMEに明記。 著作権・規約リスクを避けるのが大前提。RSS優先も権利面の安全性が理由の一つ（サイトが自ら公開する正規の配信窓口）。設計判断として説明できる形にした。
運用制約 自宅Windows PC、タスクスケジューラ（ログオン時・遅延5分）で起動。VPSではcron/systemd timer。 定期実行はOS側スケジューラの仕事＝運用要件（非FR）と切り分け。アプリはヘッドレスで別プロセス実行できる設計だけを負う（機能要件と運用要件の分離）。
予算・期間 AI 月500円以内。転職活動開始の約1ヶ月前までにVPSで公開URLを提示（Phase 6）。 ポートフォリオとしての締切（公開URL）とコスト上限を前提に、Phase 5までで個人利用完成→Phase 6で公開、と段階を切った。

8品質・エラー方針

項目決めたことなぜこの設計にしたか
★エラーハンドリング方針 情報源単位で失敗分離 NFR-10／HTTPはResilience4jでリトライ・タイムアウト・サーキットブレーカー（回数・間隔は設定外部化）／重複登録のUNIQUE違反は正常系として扱う／通数上限到達で送信停止しアプリ内表示。 外部依存が多く不安定なので「1点の失敗で全体を止めない」を軸に据えた。重複を例外でなく正常系として扱うのは冪等な多重起動を許すため。
異常系の振る舞い 他情報源は続ける／LLM失敗は当該記事をスキップ（バッチは止めない）／失敗は必ず記録。 「止める・続ける・通知する」の判断を場面ごとに事前定義。バッチ全体停止は影響が大きいので、局所失敗は握って記録し前進させる。
ログ・監査の方針 ローカルファイル依存を避け、DB（CrawlLogs / NotificationLogs / LlmUsageLogs）＋標準出力に寄せる。UTF-8統一。 VPS移行時にファイルパス依存が足かせになるのを避ける NFR-09。収集・通知・LLMコストをDBに残すことで管理画面から可視化・検証できる。

9用語・ルール

項目決めたことなぜこの設計にしたか
★用語定義（ユビキタス言語） テーマ＝登録キーワード／記事＝収集した1情報／発生日＝代表日 EventDate／カテゴリ＝8区分／お気に入り＝テーマ/情報源（通知対象）／ブックマーク＝後で見る（通知対象外）／通数＝送信先×吹き出し数。全19語をテーブル/enum/機能IDに対応づけて正式化。 §1 用語定義 言葉の意味を1つに固定して、要件〜設計〜実装のズレを防ぐ。特に「お気に入り（通知する）」と「ブックマーク（通知しない）」、「テーマ（登録して収集）」と「検索（収集済みの絞り込み）」を別概念として明確化。各用語に対応テーブル/enum/IDを併記したので、要件→設計→実装→DBが用語でたどれる（トレーサビリティ）。
ビジネスルール（計算・判定） 整列キー＝COALESCE(event_date, created_at::date)／通数＝利用者数×吹き出し数／同日2回目以降は通知抑止／月コスト集計はJST月に丸めて合算。 曖昧な日付（NULL）でもタイムラインが破綻しないよう代理キーで整列。無料枠・冪等性という制約を、判定ルールとして具体化した。

10進め方・トレーサビリティ

項目決めたことなぜこの設計にしたか
★ID体系 機能 FR-xx-xx／画面 SC-xx／テーブル TBL-xxx／非機能 NFR-xx／設計判断 Dx。 要件→設計→実装→テストをIDでたどれるようにする。後工程の成果物に前工程のIDを併記させ、変更影響とトレースを効かせる（ウォーターフォールの肝）。
レビュー・承認プロセス 各工程の成果物を開発者レビュー→承認後に次工程へ。要件定義書が承認されるまで設計・実装に進まない。 前工程の確定を待って次に進むことで手戻りを抑える。工程順を守ること自体をCLAUDE.md §0の最重要ルールに据えている。
★フェーズ分割・リリース計画 Phase 0（基盤）→1（RSS収集・一覧）→2（LLM・重複排除）→3（お気に入り・検索）→4（LINE通知・冪等性）→5（管理・自動運用）→6（VPS移行・公開）。 Phase 5までで個人利用として完成、Phase 6で公開。動くものを早く出し段階的に価値を足す。優先順位（項目2）と一体で管理。
