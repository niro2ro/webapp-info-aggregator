# 単体テスト工程

クラス/メソッド単位で振る舞いを検証する工程。開発者はテスト工程が得意なので、**「何を保証するか（テスト観点）」を明文化**したうえで JUnit 5 に落とす。

## 前提

- 対象モジュールが `04_実装/` に実装済みで、詳細設計（`03_詳細設計/`）に対応していること。
- テストコードは各 Maven モジュールの `src/test/java` に置き、仕様書・結果は `05_単体テスト/` に残す。

## 成果物

| 場所 | ファイル | 内容 |
|---|---|---|
| `05_単体テスト/` | `単体テスト仕様書.md` | テストケース一覧（`UT-001`…）。対象クラス・メソッド、観点、入力、期待結果、対応する詳細設計ID（`DD-`） |
| `05_単体テスト/` | `実施結果.md` | 実行日時、Pass/Fail 件数、`mvn test` の結果サマリ、失敗時の対応 |
| `04_実装/*/src/test/java` | JUnit 5 テストコード | 仕様書のケースに対応。ケースID をテスト名（`@DisplayName`）/コメントに紐づけ |

## 重点的にテストする観点（本プロジェクト固有）

- **冪等性**: 同一 URL を2回投入 → 1件しか登録されない（ユニーク制約 or 事前チェック）。同一 (user_id, article_id) を2回通知しようとしても1回だけ記録。同日2回目の通知バッチは送信0件。
- **URL 正規化 / ハッシュ**: クエリ除去・リダイレクト解決後に同一ハッシュになること。異なる記事が衝突しないこと。
- **重複排除**: タイトル類似度＋発生日でのグルーピングが期待通りか。
- **UTC ↔ JST 変換**: 保存は UTC（`Instant`）、表示は JST（`ZoneId.of("Asia/Tokyo")`）。境界（日付をまたぐ時刻）で正しいか。夏時間のない JST でズレないか。
- **日付の表記ゆれ**: 「9月上旬」「秋頃」「予約受付中」が要件どおりのカラム/精度フラグに格納されるか。
- **失敗分離**: 1情報源が例外を投げても他情報源の収集が継続すること。Resilience4j のリトライ回数・タイムアウトが設定どおりか。
- **LINE 通数**: 上限接近時に送信が停止しアプリ内表示に切り替わること。カウントが「ユーザー数×吹き出し数」で計算されること。
- **通知に LLM を呼ばない**こと（LLM クライアントのモックが通知経路で呼ばれない検証）。

## テスト設計の作法

- 外部依存（HTTP・DB・Claude API・LINE API）は Mockito のモック/フェイクに差し替える。DI 境界を使う（詳細設計の DI 設計を活用）。コンストラクタ注入なので `@ExtendWith(MockitoExtension.class)` で組み立てやすい。
- DB 依存ロジックは、可能なら純粋関数に切り出して単体化。統合的な DB 検証（本物の PostgreSQL）は Testcontainers を使う結合テスト工程へ回す。
- 時刻依存は `Clock` を注入してテスト可能にする（`Clock.fixed(...)`）。仮想スレッド前提のブロッキング処理はそのまま同期的に検証できる。
- 1テスト1観点。Arrange-Act-Assert を明確に。アサーションは AssertJ（`assertThat`）を基本とする。

## 実行

```bash
mvn -q test              # 全モジュール
mvn -q -pl aggregator-domain test   # モジュール個別
```

## 完了条件

仕様書の全ケースが実装され、`実施結果.md` に Pass が記録されていること（Fail は原因と対応を記載）。カバレッジより**制約（冪等性・UTC・失敗分離）の網羅**を優先する。完了後 `06_結合テスト`（`integration-testing` skill）へ。
