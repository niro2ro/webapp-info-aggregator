# 要件定義工程

ウォーターフォールの最初の工程。**ここで決めきることが後工程の手戻りを防ぐ。** いきなり実装や設計に進まない。

## 入力

- [`要件定義のためのもの/PROJECT_BRIEF.md`](../../../../要件定義のためのもの/PROJECT_BRIEF.md) — 確定事項と未決事項が混在した要件ブリーフ
- ルートの `CLAUDE.md` の設計制約（§5）

## この工程の進め方

1. **PROJECT_BRIEF を精読する。** 確定事項（DB=PostgreSQL、UTC保存、冪等性、LINE無料枠、権利配慮など）はそのまま制約として引き継ぐ。
2. **§10 の未決事項を開発者に質問する。** 勝手に決めない。少なくとも以下:
   - 対象範囲（アニメ/漫画限定か汎用か）、カテゴリ5分類の妥当性
   - 最初に実装する情報源3つ（各 RSS 提供の有無・利用規約上の可否を調査してから提示）
   - Web 構成（Vaadin Flow か Thymeleaf+htmx か REST API+別フロントか）/ LLM は Claude API でよいか / 日本語全文検索の要否
   - **日付の表記ゆれの格納方式**（確定日カラム＋曖昧表現カラム＋精度フラグ 等）← 最優先で確定
3. 回答を踏まえて成果物を作成する。曖昧な要件は残さず、決めた理由も書く。

## 成果物（`01_Requirements/` に作成）

| ファイル | 内容 |
|---|---|
| `要件定義書.md` | 全体をまとめた正本。以下を含む |
| ├ 機能一覧 | 機能ID（`FR-001`…）付き。BRIEF §4 の機能を漏れなく展開 |
| ├ 非機能要件 | 性能・データ保持・AIコスト・冪等性・移行性・障害時（BRIEF §5） |
| ├ 画面一覧 | 画面ID（`SC-01`…）付き。一覧/テーマ管理/お気に入り/管理画面 等 |
| ├ テーブル定義 | **DDL レベル**。テーブルID（`TBL-Articles`…）、PK/FK/ユニーク制約/インデックス。BRIEF §7 を出発点に確定 |
| ├ 外部I/F仕様 | Claude API（構造化）・LINE Messaging API（push/カルーセル）・収集対象（RSS/HTML）の入出力 |
| └ エラーハンドリング方針 | 情報源単位の失敗分離、リトライ方針、通数上限到達時の挙動、ログ方針 |
| `未決事項回答ログ.md` | 開発者への質問と回答の記録（意思決定の根拠を残す） |

## チェックリスト（成果物確定前に確認）

- [ ] BRIEF の確定制約がすべて要件に反映されているか（UTC保存・冪等性・LLM通知時不使用・権利配慮・LINE通数カウント）
- [ ] 冪等性が DB 制約レベルで表現されているか（`Articles.UrlHash` ユニーク、`ArticleNotifications(UserId,ArticleId)`）
- [ ] 日付の表記ゆれの格納方式が確定しているか
- [ ] 各機能に機能ID、各画面に画面ID、各テーブルにIDが振られ、後工程が参照できるか
- [ ] VPS 移行を阻害する要件が紛れていないか（Windows固有・SQLite前提など）
- [ ] 未決事項がすべて解消（または「Phaseで先送り」と明記）されているか

## 完了条件

要件定義書が開発者のレビューを受けて承認されること。承認後に `02_BasicDesign`（`basic-design` skill）へ進む。
**レビュー前に設計・実装へ進まない。**
