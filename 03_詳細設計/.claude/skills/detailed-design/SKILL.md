# 詳細設計工程（内部設計）

基本設計で決めた「外から見える振る舞い」を、**実装できる内部構造**へ落とす工程。C# 実務未経験の開発者がレビューできるよう、**.NET 固有の設計判断には必ず理由を書く**（ルート CLAUDE.md §0-3, §2）。

## 前提

- `02_基本設計/` 一式が**レビュー承認済み**であること。
- 技術構成（CLAUDE.md §4）と設計制約（§5）を守る。ライブラリの使い方は着手時に公式ドキュメントで確認する。

## .NET 固有で「理由を書く」対象（省略しない）

- async/await を使う箇所と使わない箇所の切り分け（I/O バウンドなバッチ収集はなぜ非同期か）
- HttpClientFactory を直接 new しない理由（ソケット枯渇・DNS 更新）
- DI ライフタイムの選択理由（DbContext がなぜ Scoped か 等）
- LINQ の使いどころ（可読性 vs パフォーマンス）
- record / nullable 参照型 / DTO とエンティティの分離方針

## 設計上の必須ポイント

- **収集と通知を別プロセス/別エントリポイント**として設計（Generic Host のコンソールアプリ）。
- **冪等性**を実装レベルで固定: URL 正規化ロジック、ハッシュ生成、`SaveChanges` 時のユニーク制約違反ハンドリング、未通知フラグ更新のトランザクション境界。
- **UTC**: エンティティは `DateTime`(UTC) or `DateTimeOffset`。JST 変換は表示層に閉じる。`TimeZoneInfo` の識別子直書き禁止 → 変換ヘルパーに集約。
- **OS非依存**: パスは `Path.Combine`、ローカルファイル依存を避ける。VPS 移行時にコード変更が要らない設計。
- **LLM は収集の構造化のみ**。通知経路に LLM 呼び出しを一切置かない。

## トレーサビリティ

各クラス/モジュールに詳細設計ID（`DD-...`）を振り、基本設計ID（`BD-`）と要件ID（`FR-`）へ遡れる対応表 `設計トレース表.md` を残す。
