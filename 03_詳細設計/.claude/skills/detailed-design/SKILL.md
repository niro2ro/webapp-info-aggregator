# 詳細設計工程（内部設計）

基本設計で決めた「外から見える振る舞い」を、**実装できる内部構造**へ落とす工程。Java 実務未経験の開発者がレビューできるよう、**Java / Spring 固有の設計判断には必ず理由を書く**（ルート CLAUDE.md §0-3, §2）。

## 前提

- `02_基本設計/` 一式が**レビュー承認済み**であること。
- 技術構成（CLAUDE.md §4）と設計制約（§5）を守る。ライブラリの使い方は着手時に公式ドキュメントで確認する。

## Java / Spring 固有で「理由を書く」対象（省略しない）

- ブロッキング処理と仮想スレッド（Java 21 Loom）の使い分け（I/O バウンドなバッチ収集をなぜ仮想スレッドで並行化するか。async/await 相当を避けられる理由）
- `RestClient` を都度 new せず Bean 化する理由（コネクション管理・共通設定の集約）
- Bean スコープの選択理由（リポジトリ/サービスがなぜ singleton か、状態を持つ処理をどう扱うか）
- Stream API（LINQ 相当）の使いどころ（可読性 vs パフォーマンス）
- `record` / DTO とエンティティの分離方針、`Optional` による null 表現
- JPA の遅延ロード・トランザクション境界（`@Transactional`）・N+1 問題への対処

## 設計上の必須ポイント

- **収集と通知を別プロセス/別エントリポイント**として設計（Spring Boot 別アプリ + `CommandLineRunner`）。
- **冪等性**を実装レベルで固定: URL 正規化ロジック、ハッシュ生成、`save`/`flush` 時のユニーク制約違反（`DataIntegrityViolationException`）ハンドリング、未通知フラグ更新のトランザクション境界。
- **UTC**: エンティティは `Instant`（UTC）で保持。JST 変換は表示層に閉じ、`ZoneId.of("Asia/Tokyo")` を変換ヘルパー一箇所に集約（識別子の直書き分散を禁止）。
- **OS非依存**: パスは `Path.of(...)`、ローカルファイル依存を避ける。VPS 移行時にコード変更が要らない設計。
- **LLM は収集の構造化のみ**。通知経路に LLM 呼び出しを一切置かない。
