DBMS PostgreSQL（Docker Compose でローカル起動・D8）
マイグレーション Flyway（V1__init.sql に本書の DDL を反映。SQL ベース管理）

本書は要件定義 §6 の論理DDLを物理テーブル定義として正式化する。物理テーブル名・カラム名は PostgreSQL 慣習の snake_case、JPA エンティティ側は camelCase（@Column/命名戦略でマッピング）。列挙型は smallint（コード値）で保持し、Hibernate 既定の @Enumerated(ORDINAL) は使わず AttributeConverter（@Convert）でコード値を明示変換する（列挙順への暗黙依存を避ける）。

0. 共通方針

事項 方針 根拠
主キー サロゲート id bigint（GENERATED BY DEFAULT AS IDENTITY）。中間テーブルは自然キーの複合PK —
日時 すべて timestamptz（UTC保存）。表示直前に JST 変換。event_date のみ date（時刻を持たない代表日） NFR-08
列挙型 smallint コード値＋COMMENT。アプリ enum と AttributeConverter で相互変換 §6
文字列 原則 text（PostgreSQL では varchar(n) と性能差なし）。モデル名のみ varchar(100) —
命名 テーブル＝複数形 snake_case（例 article_theme_matches）、カラム＝snake_case —
制約名 pk_ / fk_ / uq_ / ix_ 接頭辞で明示（物理名は詳細設計で最終確定） —
文字コード データベース／接続とも UTF-8 §9

列挙値の定義（コード値）

enum コード: 意味
Category 1:グッズ / 2:アニメ / 3:漫画 / 4:イベント / 5:ゲーム / 6:ゲームセンター / 7:カプセルトイ(ガチャ) / 9:その他
EventDatePrecision 0:Exact(確定日) / 1:Month(月まで) / 2:Season(季節・曖昧) / 3:Ongoing(受付中/発売中等) / 9:Unknown
EventDateKind 1:発売日 / 2:開催日 / 3:放送日 / 4:受付開始 / 9:その他
FetchType 1:Rss（RSS のみ。旧 2:HtmlParser・3:Llm は廃止。旧データの 2・3 は読込時 Rss にフォールバック）
CrawlStatus 0:Success / 1:PartialError / 2:Failed
LlmCallStatus 0:Success / 1:Failed / 2:FormatError（応答JSON不正・当該記事のみスキップ）
UserRole 1:User(一般) / 9:Admin(管理者)
NotifyStatus 0:Success / 1:TempError / 2:RateLimited / 3:AuthFailed / 4:Blocked / 5:FormatError / 6:Timeout / 9:GaveUp

将来カテゴリ等が増える場合はアプリ側 enum にコードを追加するだけでよく、スキーマ変更は不要（要件レビュー第2回で承認済みの方針）。

2. 収集データ（本体）

2.1 articles（TBL-Articles）— 記事

論理 物理カラム 型 制約 説明
ID id bigint PK
取得元 source_id bigint NOT NULL, FK→sources(id) ON DELETE RESTRICT
見出し title text NOT NULL
カテゴリ category smallint NOT NULL Category enum
実イベント日（代表日） event_date date NULL 発売日/開催日/放送日など記事を読んで分かる実際の日付。LLM/パーサーが埋める（不明は NULL）。並び替え・期間フィルタ用
掲載日 published_at timestamptz NULL 記事が配信された日時（RSSの日付）＝「記事発生日」。V4で追加。event_date と役割分離
発生日原文 event_date_text text NULL 「9月上旬」等・表示用
発生日精度 event_date_precision smallint NOT NULL DEFAULT 9 EventDatePrecision enum
発生日種別 event_date_kind smallint NOT NULL DEFAULT 9 EventDateKind enum。表示ラベル・発売日順ソート用
場所 location text NULL イベント時のみ
元URL url text NOT NULL
URLハッシュ url_hash text NOT NULL, UNIQUE 正規化URLのハッシュ（重複登録防止＝冪等性の一次担保）
タイトルキー title_key text NULL 重複判定用の正規化タイトル（末尾「 - 媒体名」除去）。同一タイトルの記事を1件に集約（V5追加・FR-02-09）
要約 summary text NULL 自作要約（本文は保存しない・§9 権利配慮）
グループキー group_key text NULL 類似グルーピング（別サイト同一情報の束ね）
収集日時 created_at timestamptz NOT NULL DEFAULT now() UTC

インデックス:

名称 対象 目的
uq_articles_url_hash UNIQUE(url_hash) 冪等性の一次担保（FR-02-08）
ix_articles_event_date (event_date) 期間フィルタ・発売日順
ix_articles_created_at (created_at) 収集日順
ix_articles_source_id (source_id) 情報源絞込
ix_articles_category (category) カテゴリ絞込
ix_articles_timeline ((COALESCE(event_date, (published_at AT TIME ZONE 'UTC')::date, (created_at AT TIME ZONE 'UTC')::date))) タイムライン整列キーの式インデックス（FR-04-01・一覧応答2秒 NFR-04）。代表日＝実イベント日→掲載日→収集日 の順にフォールバック（V4で published_at を追加）。※timestamptz::date は固定ゾーン(UTC)へ変換してから date 化（IMMUTABLE要件）
ix_articles_published_at (published_at) 掲載日順ソート（V4追加）
gin_articles_title_trgm GIN(title gin_trgm_ops) pg_trgm 部分一致検索（FR-04-03）
gin_articles_summary_trgm GIN(summary gin_trgm_ops) 同上

タイムライン整列キー = COALESCE(event_date, (created_at AT TIME ZONE 'UTC')::date)。event_date が NULL（precision=Unknown/Ongoing）の記事は収集日で代理整列し、降順では新着として上位に来る。式インデックスで NFR-04 を担保。一覧クエリの ORDER BY も同一式を使うこと（そうしないと index が効かない）。※created_at::date を直接使うと PostgreSQL の「index 式は IMMUTABLE 必須」に反する（timestamptz→date はTZ依存）ため UTC 固定で date 化する（実装Phase0で確定）。 前提拡張: CREATE EXTENSION IF NOT EXISTS pg_trgm;（Flyway の初期マイグレーションで実行）。

論理 物理カラム 型 制約 説明

3.5 article_notifications（TBL-ArticleNotifications）— 記事別通知履歴（再送防止）

論理 物理カラム 型 制約 説明
利用者ID user_id bigint NOT NULL, FK→users(id) ON DELETE CASCADE
記事ID article_id bigint NOT NULL, FK→articles(id) ON DELETE CASCADE
通知/打切日時 notified_at timestamptz NOT NULL DEFAULT now() UTC
結果 result smallint NOT NULL DEFAULT 0 0:Delivered / 1:GaveUp（打ち切り＝再送しない）
  • 主キー: pk_article_notifications (user_id, article_id)（重複通知防止＝冪等）
  • 未通知＝本テーブルに行が無い状態。送信失敗（①②③⑤）では行を作らず次回起動で再送。成功（Delivered）と打ち切り（GaveUp＝④形式エラー／③の5日超過）でのみ行を作り再送対象から外す。GaveUp は SC-02 で「未通知（未達）」として可視化（FR-04-06）。

4. ログ／実績

4.1 notification_logs（TBL-NotificationLogs）— 通知ログ・通数カウント

論理 物理カラム 型 制約 説明
ID id bigint PK
送信先 user_id bigint NOT NULL, FK→users(id) ON DELETE CASCADE
送信日時 sent_at timestamptz NOT NULL DEFAULT now() UTC
記事件数 article_count int NOT NULL 束ねた記事件数
消費通数 message_count int NOT NULL 送信先×吹き出し数
送信結果 status smallint NOT NULL NotifyStatus enum
  • インデックス: ix_notification_logs_sent_at (sent_at)
  • 月間通数 = sent_at を JST 月に丸めて SUM(message_count)。上限接近判定（FR-06-04）。
  • 保持: 1ヶ月（NFR-05）。

4.2 crawl_logs（TBL-CrawlLogs）— 収集ログ

開始 started_at timestamptz NOT NULL DEFAULT now() UTC
終了 finished_at timestamptz NULL UTC

4.3 llm_usage_logs（TBL-LlmUsageLogs）— LLM利用ログ・コストカウント

論理 物理カラム 型 制約 説明
ID id bigint PK
呼び出し日時 called_at timestamptz NOT NULL DEFAULT now() UTC
モデル model varchar(100) NOT NULL 単価が変わるため保持
入力トークン input_tokens int NOT NULL DEFAULT 0 API レスポンスの usage 値
出力トークン output_tokens int NOT NULL DEFAULT 0 同上
概算コスト est_cost_micro_jpy bigint NOT NULL DEFAULT 0 マイクロ円（円×100万）。単価×トークンを整数保持し丸め誤差回避。表示時 ÷1,000,000
収集ログID crawl_log_id bigint NULL, FK→crawl_logs(id) ON DELETE SET NULL どの収集実行に紐づくか（トレース用・任意）
ステータス status smallint NOT NULL LlmCallStatus enum
  • インデックス: ix_llm_usage_logs_called_at (called_at)
  • 月間コスト = called_at を JST 月に丸めて SUM(est_cost_micro_jpy)（表示時に円換算）。ハードキャップ判定（NFR-06・FR-02-11）。
  • 単価は記録時に確定値を保存し、後日の単価改定で過去実績がぶれないようにする。
  • 保持: パージしない（当月・過去のコスト実績として保持）。親 crawl_logs が1ヶ月でパージされても本行は残す（SET NULL）。

5. データ保持・パージ方針（NFR-05）

対象 保持期間 パージ条件 連動削除
articles 2年 created_at が2年超 かつ どの利用者の bookmarks にも存在しない read_states / article_theme_matches / article_notifications を CASCADE
crawl_logs 1ヶ月 started_at が1ヶ月超 llm_usage_logs.crawl_log_id を SET NULL（実績は残す）
notification_logs 1ヶ月 sent_at が1ヶ月超 なし
その他マスタ・関連 恒久 利用者/テーマ/情報源の削除操作に従う（§ON DELETE） ER図 §2 参照

記事は「直近2年分」で対象期間と一致（前年同期比較のため）。ブックマーク済みは「後で見る」を消さないためパージ除外。パージ処理は Phase 5 のデータ保持タスクで実装（バッチ）。
