# 基本設計工程（外部設計）

「ユーザーや外部システムから見える振る舞い」を確定する工程。**内部のクラス構造にはまだ踏み込まない**（それは詳細設計）。

## 前提

- `01_Requirements/要件定義書.md` が**レビュー承認済み**であること。未承認なら要件定義に戻る。
- ルート `CLAUDE.md` の設計制約（§5）と技術構成（§4）を踏襲する。

## 成果物（`02_BasicDesign/` に作成）

| ファイル | 内容 |
|---|---|
| `画面設計書.md` | 画面ごとのレイアウト・項目・入出力・操作。要件の画面ID（`SC-01`…）を参照 |
| `画面遷移図.md` | 画面間の遷移。Mermaid で図示 |
| `テーブル定義書.md` | 各テーブルのカラム・型・制約・インデックス・保持期間。要件の DDL を正式化 |
| `ER図.md` | エンティティ関連。Mermaid `erDiagram` |
| `バッチ設計書.md` | **収集バッチ**と**通知バッチ**を別プロセス/別ステップとして定義。処理フロー・入出力・冪等性の担保点・取得後のLLM補完（取得方式はRSSのみ・専用パーサー/LLM取得は不採用）・失敗時の分離 |
| `外部IF設計書.md` | Claude API（構造化の入出力スキーマ）・LINE Messaging API（push/Flex カルーセル、通数カウント方法）・収集対象の取得方式一覧 |
| `メッセージ・エラー一覧.md` | 画面/ログ/通知のメッセージをID付きで一覧化 |

## 設計上の必須ポイント

- **収集と通知は分離**して設計する（通知は既存データだけで完結。LLM を呼ばない）。
- **冪等性**を処理フローで明示: 収集時の URL 正規化→ハッシュ→ユニーク制約、通知時の未通知フラグ方式＋同日2回目以降スキップ＋通数上限で送信停止。
- **日時**: 保存は UTC、表示は JST 変換。画面・帳票の表示仕様に「JST 表示」を明記。
- **日付の表記ゆれ**: 要件で決めた格納方式（確定日/曖昧表現/精度フラグ）を、画面表示ルールと突き合わせる。
- **権利配慮**: 画面には自作要約＋元URLのみ。本文・公式画像を表示しない設計にする。
- 図は Mermaid で書き、Markdown 内に埋め込む（別ツール依存を避ける）。

## トレーサビリティ

各設計項目に設計ID（`BD-...`）を振り、対応する要件ID（`FR-`, `SC-`, `TBL-`）を併記する。要件 → 基本設計の対応表を `要件トレース表.md` として残す。

## チェックリスト

- [ ] 全機能ID・全画面ID・全テーブルIDが基本設計でカバーされているか（漏れ＝要件トレース表で検出）
- [ ] 収集バッチと通知バッチが分離されているか
- [ ] 冪等性の担保点が処理フロー図に現れているか
- [ ] UTC保存/JST表示が画面・バッチ両方で一貫しているか
- [ ] VPS移行を阻害する外部依存（Windows固有・ローカルファイル依存）がないか

## 完了条件

基本設計書一式が開発者レビューで承認されること。承認後に `03_DetailedDesign`（`detailed-design` skill）へ進む。
